# 개인 프로젝트 · 취미 위시리스트와 예산 추천

구매하거나 체험하고 싶은 책·게임·운동용품·캠핑 장비 등을 관리하는 개인 프로젝트입니다. 주제와 서비스 이름은 각자 정합니다. 등록·조회뿐 아니라 내 예산으로 고를 수 있는 항목을 추천하는 기능을 만듭니다.

책의 `product-api/`는 이후 수업에서 계속 사용합니다. 개인 코드는 같은 `sesac-spring-boot-study` 저장소의 `personal-project/`에 작성하고 기존 프로젝트는 보존합니다. 아래 조건은 교재 원문을 옮긴 것이 아니라 배운 내용을 적용하기 위한 과제 요구사항입니다.

## 수업 내용

- CH 09 상품 관리와 CH 12 객체지향·테스트 설명은 책으로 진행합니다.
- 책에서 본 객체의 규칙, 저장소의 추상화, 생성자 주입, 테스트를 개인 프로젝트에 적용합니다.
- 구현 및 준비 시간은 **150분**입니다.
- 결과 발표에서는 코드·테스트·실행 화면을 사용합니다. 발표용 PPT는 만들지 않습니다.

## 7일 기본 요구사항

### 데이터

`CollectionItem`에 `id`, `name`, `price`를 둡니다. `name`은 위시리스트 항목 이름, `price`는 원 단위 정수 가격입니다.

- 이름이 `null`이거나 비어 있거나 공백뿐이면 거부합니다. 저장할 때 이름 앞뒤 공백을 제거합니다.
- 가격은 0 이상입니다. 무료 항목도 등록할 수 있습니다.
- id는 프로그램에서 부여하고 조회할 때 실제 등록 결과의 id를 사용합니다. 번호의 연속성은 가정하지 않습니다.

### 기능

| 기능 | 요구사항 |
| --- | --- |
| 등록 | 이름과 가격을 받아 항목 저장 |
| 목록 조회 | 전체 항목 반환, 데이터가 없으면 빈 목록 |
| 단건 조회 | id로 항목 조회, 없는 id는 예외로 구분 |
| 예산 추천 | 각 항목의 가격이 예산 이하인 구매 후보를 가격 오름차순으로 최대 3개 반환 |

가격이 같은 항목은 등록 순서대로 추천합니다. 예산 0이면 무료 항목만 추천하고, 음수 예산은 거부합니다. 추천할 항목이 없으면 빈 목록을 반환합니다. 조회·추천으로 원본 데이터나 전체 목록의 순서가 바뀌면 안 됩니다.

### 추천 예시

아래 순서로 등록했다고 가정합니다.

| 항목 | 가격 |
| --- | ---: |
| 노트 | 12000 |
| 무료 샘플 | 0 |
| 펜 | 5000 |
| 스티커 | 5000 |
| 게임 | 8000 |

- 예산 5000 → 무료 샘플, 펜, 스티커
- 예산 0 → 무료 샘플
- 음수 예산 → 예외
- 항목이 없는 저장소 → 빈 목록

## 구조와 테스트

- Domain 객체가 이름·가격의 규칙을 지킵니다.
- Repository 인터페이스와 메모리 구현을 분리합니다. 저장·조회 코드는 저장소가 맡습니다.
- Service가 등록·조회·추천을 처리하고, Repository 인터페이스를 생성자로 받습니다.
- Spring이 Service와 Repository를 생성·연결한 결과를 실제로 확인합니다. 웹 서버 없이 컨텍스트 테스트로 확인해도 됩니다.
- 단위 테스트는 Spring 없이 새 저장소를 전달해 실행하고 테스트 간 데이터가 섞이지 않게 합니다.

최소 4개의 단위 테스트를 작성합니다. 정상 등록·조회, 잘못된 이름·가격, 추천 경계·정렬·최대 개수, 빈 결과·원본 보존을 확인합니다. 기대값과 실제 결과를 비교하고, 단순히 예외 없이 실행된 것만으로 성공이라고 기록하지 않습니다.

기본 과제에는 HTTP 서버·DB·프론트엔드가 필요하지 않습니다. 정답 코드 대신 책과 본인이 작성한 코드·테스트를 사용합니다.

기본 기능과 테스트를 완료했다면 다음 중 선택합니다.

- 즐겨찾기 또는 구매 완료 상태와 상태별 목록
- AOP로 Service의 실행 시간 기록: 직접 생성한 객체 호출과 Spring이 연결한 객체 호출의 차이 확인

새 기능에도 정상·실패 테스트를 추가하고 기본 동작은 유지합니다.

## AI 프론트엔드 · 선택 과제

AI를 활용해 위시리스트 목록, 항목 등록 폼, 예산 입력, 추천 결과 화면을 만듭니다.

- 순수 HTML·CSS·JavaScript만 사용합니다. 외부 라이브러리와 CDN은 사용하지 않습니다.
- 프롬프트와 화면 디자인은 자율입니다. 생성된 코드를 직접 실행하고 수정한 내용을 설명합니다.
- 기본 Java 코어만 만들었다면 샘플 데이터로 화면부터 만들 수 있습니다. 이때 실제 서버 연동으로 표시하지 않습니다.
- 실제 연동까지 도전하려면 책 9장의 REST API 부분을 참고해 HTTP API를 추가하고 `fetch`로 연결합니다. 브라우저에서 Java Service를 직접 호출할 수는 없습니다.
- API를 추가했다면 Controller는 요청·응답을, Service는 업무 처리를 맡습니다. 경로·입력·응답 계약을 README에 적고 실제 네트워크 요청과 결과를 확인합니다.
- 백엔드 핵심 로직은 직접 구현합니다. 화면에서만 데이터를 바꾸고 서버에도 저장됐다고 설명하지 않습니다.

## 이론 적용 체크리스트

다른 교육생의 코드·실행 결과와 함께 확인합니다.

- [ ] 이름·가격 규칙이 Domain에 있고, 잘못된 값이 저장되지 않는가?
- [ ] 저장·조회는 Repository가 담당하고 Service에 저장소 내부 자료구조가 노출되지 않는가?
- [ ] Service가 구현 클래스 대신 Repository 인터페이스를 생성자로 받는가?
- [ ] Spring이 객체를 연결한 결과와 직접 생성한 단위 테스트를 구분해 확인했는가?
- [ ] 테스트가 정상·실패·추천 결과를 비교하고, 실행 순서에 의존하지 않는가?
- [ ] 예산 경계·동일 가격의 등록 순서·최대 3개·원본 보존을 지키는가?
- [ ] 추가 AOP를 구현했다면 공통 로그와 업무 코드가 분리됐는가?
- [ ] HTTP·프론트를 추가했다면 요청 → Controller → Service → 응답 흐름을 설명할 수 있는가?

## 9일 과제 · 외부 상품 연동과 장바구니

기존 위시리스트에 **외부에서 검색한 상품을 담고, 쿠폰과 배송비를 반영한 금액을 확인하는 기능**을 추가합니다. 직접 등록한 상품과 외부 상품을 같은 위시리스트·장바구니에서 사용합니다. 개인 Fork의 기존 `personal-project/`에서 이어서 구현하며 항목 등록·조회·추천과 기존 테스트는 유지합니다.

먼저 자기 PR에서 발견한 입력 누락·`null` 처리, HTTP 400/404, 도메인 규칙과 실패 후 데이터 보존 문제를 보완합니다. **1·2단계는 필수, 3단계는 추가 도전입니다.** 수업 중 공통 목표는 1단계이며 2단계는 과제로 이어서 완성합니다. 마감은 별도로 안내합니다. 메모리 저장소를 사용하며 DB·로그인·실제 결제는 요구하지 않습니다.

### 사용할 상품 데이터

[DummyJSON 상품 API 공식 문서](https://dummyjson.com/docs/products)를 확인합니다. 상품에는 `id`, `title`, `price`, `category`, `thumbnail`, `stock` 등이 있습니다. 데이터의 개수·id·가격·재고를 프로그램에 고정하지 않습니다.

| 기능 | 외부 API 예시 |
| --- | --- |
| 상품 목록 | `GET https://dummyjson.com/products?limit=10&skip=0` |
| 상품 검색 | `GET https://dummyjson.com/products/search?q=phone&limit=10&skip=0` |
| 상품 상세 | `GET https://dummyjson.com/products/1` |

요청 흐름은 **브라우저 → 내 Spring 서버 → DummyJSON**입니다. 이때 내 서버도 DummyJSON에 대해서는 클라이언트 역할을 합니다. 외부 API는 조회만 사용합니다. DummyJSON의 추가·수정·삭제는 영구 저장이 아닌 모의 동작이므로 찜과 장바구니는 자신의 메모리 저장소에 저장합니다. 쿠폰·배송비·수량·가격 환산은 외부 서비스의 정책이 아니라 이번 과제에서 정한 규칙입니다.

이번 과제에서 `price`는 **API 가격 1단위 = 1,000원**이라는 고정 기준으로 변환합니다. 실제 환율을 조회하거나 API의 통화를 가정하는 규칙이 아닙니다. `BigDecimal`로 1,000을 곱하고 원 미만은 `HALF_UP`으로 반올림합니다. 예를 들어 `9.99`는 9,990원입니다. 변환한 개별 가격은 기존 정수 가격 범위 안인지 확인하고, 수량 곱셈·합계는 처음부터 `long` 연산으로 계산합니다.

`discountPercentage`는 이번 계산에 사용하지 않습니다. 쿠폰은 아래 과제 규칙으로 직접 구현합니다. 외부의 `minimumOrderQuantity`도 사용하지 않고 수량은 과제의 1~5개 규칙을 따릅니다. `stock`은 가져온 시점의 참고 재고이며 예약하거나 외부 서버에서 차감하지 않습니다.

### 1단계 · 상품 검색과 위시리스트에 담기

- **Spring 서버가 DummyJSON을 호출**하고, 자체 API로 상품 목록·검색·상세 결과를 제공합니다. 화면이 외부 API를 직접 호출하는 것만으로 완료하지 않습니다.
- 목록·검색은 `limit` 기본 10, 허용 범위 1~20, `skip` 기본 0이며 음수는 거부합니다. 검색어 누락·공백은 400으로 거부하고, 검색 결과가 없으면 200과 빈 목록을 반환합니다.
- 외부 상품 id를 받아 위시리스트에 담습니다. 요청에서 받은 상품명·가격을 그대로 저장하지 않고, 서버가 외부 상세 API로 확인한 이름·원화 가격·카테고리·이미지·재고를 저장합니다.
- 내 위시리스트 id와 외부 상품 id를 구분합니다. 직접 등록한 항목인지 DummyJSON에서 가져온 항목인지도 저장합니다. 같은 외부 상품을 두 번 담으면 409로 거부합니다.
- 품절 상품도 찜할 수 있습니다. 장바구니에 담을 때는 재고 규칙을 적용합니다.
- 외부 상품은 가져온 당시 값을 보관합니다. 필수 범위에서는 자동 가격·재고 갱신을 구현하지 않습니다. 외부 상품의 이름·가격을 임의의 요청값으로 수정하는 것은 거부하고, 직접 등록한 항목의 기존 수정 동작은 유지합니다.
- 외부에 없는 상품은 404, 외부 응답 지연·통신 실패는 502로 구분합니다. 연결·응답 대기 시간을 유한하게 정하고, 실패한 가져오기는 일부 데이터도 저장하지 않습니다. 응답에 필수 값이 없거나 사용할 수 없는 상품 데이터이면 저장하지 않고 502로 처리합니다.

### 2단계 · 장바구니와 쿠폰 금액 계산

서버에 장바구니 하나를 두고 목록 조회·상품 추가·수량 변경·삭제를 제공합니다. 장바구니는 메모리에 저장하며 재시작하면 초기화돼도 됩니다.

- 내 위시리스트 id와 수량으로 담습니다. 수량 누락·`null`·0·음수·6 이상은 거부하고, 서로 다른 상품은 최대 20종류까지 담습니다.
- 같은 항목을 다시 담으면 기존 수량에 더합니다. 합친 수량도 1~5개여야 합니다. 직접 등록한 항목은 외부 재고 제한이 없고, 외부 상품은 저장한 `stock`을 초과할 수 없습니다. 품절 상품은 장바구니에 담을 수 없습니다.
- 처음 담을 때 항목의 이름·가격·재고를 장바구니에 복사합니다. 같은 항목을 다시 담거나 수량만 바꾸면 기존 장바구니의 복사본을 사용합니다. 위시리스트 원본이 수정·삭제돼도 담아 둔 내용은 바뀌지 않습니다. 삭제 후 다시 담으면 그때의 위시리스트 값을 새로 복사합니다.
- 추가는 위시리스트에 항목이 있어야 합니다. 기존 장바구니의 수량 변경·삭제는 장바구니 항목 id를 사용하므로 위시리스트 원본이 삭제돼도 가능합니다.
- 없는 항목은 404, 잘못된 수량은 400, 재고·합산 수량·종류 수 한도 충돌은 409로 응답합니다. 실패하면 기존 장바구니의 모든 데이터가 유지돼야 합니다.

금액 미리보기 요청에서 `couponCode`를 받습니다. 생략하면 `NONE`이며, `null`·모르는 코드는 400으로 거부합니다. 쿠폰은 미리보기에서만 적용하고 장바구니에 선택 상태를 저장하거나 사용 횟수를 차감하지 않습니다.

| 쿠폰 코드 | 규칙 |
| --- | --- |
| `NONE` | 할인 없음 |
| `PERCENT10` | 상품 합계의 10% 할인, 원 미만 버림, 최대 20,000원 |
| `FIXED15000` | 할인 전 상품 합계가 100,000원 이상일 때 15,000원 할인 |

- 한 번에 쿠폰 하나만 적용합니다. 조건을 만족하지 못한 쿠폰은 400으로 거부하며 장바구니를 바꾸지 않습니다.
- 상품 합계는 각 상품의 `원화 단가 × 수량`을 모두 더합니다. 여기에 쿠폰을 적용하고 **할인 후 상품 금액**이 100,000원 이상이면 무료 배송, 미만이면 배송비 5,000원을 더합니다.
- 빈 장바구니는 상품 합계·할인액·배송비·최종 금액이 모두 0원입니다. 빈 장바구니에는 `NONE`만 허용합니다.
- 결과에는 쿠폰 코드, 상품 합계, 할인액, 할인 후 상품 금액, 배송비, 최종 금액을 구분해 반환합니다. 실제 주문·결제·외부 재고 차감은 하지 않습니다.

계산 순서를 이해하기 위한 예시입니다. 실제 QA의 입력값과 확인 순서는 직접 설계합니다.

| 상품 합계 110,000원 | 할인액 | 할인 후 상품 금액 | 배송비 | 최종 금액 |
| --- | --- | --- | --- | --- |
| `NONE` | 0원 | 110,000원 | 0원 | 110,000원 |
| `PERCENT10` | 11,000원 | 99,000원 | 5,000원 | 104,000원 |
| `FIXED15000` | 15,000원 | 95,000원 | 5,000원 | 100,000원 |

### 3단계 · 가장 유리한 쿠폰 추천

현재 장바구니에서 `NONE`과 사용 가능한 쿠폰을 각각 계산해 **배송비를 포함한 최종 금액이 가장 낮은 선택**을 추천합니다. 할인액만 비교하면 안 됩니다. 최종 금액이 같으면 `NONE` → `PERCENT10` → `FIXED15000` 순서로 고릅니다. 빈 장바구니는 `NONE`·0원을 반환합니다. 추천으로 장바구니 내용이 바뀌면 안 됩니다.

빠르게 끝냈다면 AI로 상품 검색·위시리스트·장바구니·쿠폰 미리보기 화면을 추가합니다. **HTML·CSS·순수 JavaScript만 사용하고 외부 라이브러리와 JS·CSS CDN은 사용하지 않습니다. 상품 이미지는 DummyJSON의 이미지 URL을 사용할 수 있습니다.** 프롬프트는 자율이며 화면은 본인의 Spring API를 호출합니다. 프론트엔드는 추가 과제입니다.

### 설계와 QA

API 경로와 요청·응답 형식은 직접 정해 README에 기록합니다. 외부 API 주소는 지정된 DummyJSON을 사용하고, 사용자가 임의의 외부 URL을 입력하게 만들지 않습니다.

- Controller: HTTP 입력·응답과 DTO 검증
- Domain: 수량·쿠폰·배송비·금액 계산 규칙
- Service: 외부 상품 조회와 가져오기, 위시리스트·장바구니 처리 흐름 조율
- Repository: 저장·조회 인터페이스와 메모리 구현
- 외부 API 클라이언트: DummyJSON 통신과 응답 변환을 별도 클래스로 분리

생성자 주입을 사용하고 Controller에 통신·저장·금액 계산을 몰아넣지 않습니다. HTTP 클라이언트 선택은 자율입니다.

정상 동작·잘못된 입력·경계 조건·외부 API 실패·실패 후 데이터 보존을 고려해 **QA 체크리스트를 직접 작성하고 실행**합니다. 구체적인 확인 항목·입력값·기대 결과·실제 결과는 본인이 정리합니다. 기존 테스트를 유지하고 금액 계산·쿠폰 조건·실패 후 장바구니 보존·복사한 값의 보존에 의미 있는 테스트를 추가합니다. 외부 API는 테스트용 대체 구현으로 성공·실패를 재현해, 테스트가 실제 인터넷 응답에 의존하지 않게 합니다.

README에 실행 방법, API 계약, 가격 변환·쿠폰·배송비 규칙, 클래스별 책임, QA·테스트 결과, 발견한 문제와 수정 내용, 단계별 완료·미완료 범위를 적습니다.

설계 확인용 체크리스트입니다. 직접 작성할 QA 체크리스트를 대신하지 않습니다.

- [ ] 기존 수동 등록·추천 기능과 테스트를 유지했는가?
- [ ] 외부 id와 내 항목 id를 구분하고 서버가 상품 정보를 확인하는가?
- [ ] 도메인이 수량·금액 규칙을 지키고 실패하면 기존 데이터가 유지되는가?
- [ ] 외부 통신·업무 처리·저장의 책임이 분리되고 생성자 주입을 사용하는가?
- [ ] 외부 응답을 그대로 노출하는 대신 필요한 요청·응답 DTO를 설계했는가?
- [ ] 할인액과 배송비를 따로 설명하고 최종 금액 계산을 테스트했는가?

## 14일 확장

같은 개인 프로젝트에 책에서 배운 REST CRUD·입력 검증·예외 처리를 적용합니다. 7일의 추천 기능과 테스트는 유지합니다.

| 요청 | 성공 | 실패 |
| --- | --- | --- |
| `POST /items` | 201, 생성된 항목 JSON과 `Location` | 잘못된 이름·가격 400 |
| `GET /items` | 200, 목록 JSON, 없으면 `[]` | — |
| `GET /items/{id}` | 200, 항목 JSON | 없는 id 404 |
| `PUT /items/{id}` | 200, 수정된 항목 JSON, id 유지 | 없는 id 404, 잘못된 이름·가격 400 |
| `DELETE /items/{id}` | 204, 본문 없음 | 없는 id 404 |

요청은 `name`, `price`, 단건 응답은 `id`, `name`, `price`를 사용합니다. 이름 누락·공백과 가격 누락·`null`·음수를 거부하고 실패 전후 데이터가 유지되는지 확인합니다. 없는 id와 잘못된 입력은 각각 따로 테스트합니다.

추천을 API로 제공하는 것은 선택입니다. 예를 들어 `GET /items/recommendations?budget=5000`을 추가할 수 있으며, 경로와 응답은 README에 명시합니다. 메모리 저장소이므로 재시작 후 데이터가 사라져도 됩니다. JPA·DB·로그인·프론트는 기본 요구가 아닙니다.

구현 및 준비는 150분입니다. 미완료라면 동작하는 한 기능과 막힌 원인·다음 작업도 발표합니다.
