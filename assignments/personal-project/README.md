# 주말 개인 프로젝트 · 나만의 소장품 관리

책에서 함께 만든 상품 관리 기능을 다른 주제에 직접 적용합니다. 책·게임·운동용품처럼 본인이 설명할 수 있는 소장품 한 종류를 고르세요. 혼자 구현하고, 본인의 코드와 실행 결과로 발표합니다.

책의 공통 프로젝트 `product-api/`와 개인 프로젝트 `personal-project/`는 구분합니다. 공통 프로젝트는 이후 REST·JPA 수업에서 계속 사용하므로 지우거나 개인 프로젝트로 바꾸지 않습니다. 새 GitHub 저장소는 만들지 않고 개인 계정의 `sesac-spring-boot-study` 안에 두 폴더를 유지합니다.

아래 기능과 응답 기준은 개인 과제를 위한 수업 규칙입니다. 교재 원문을 그대로 옮긴 요구사항이 아닙니다. 교재의 관련 코드는 참고할 수 있지만, 개인 과제의 완성 정답 코드는 제공하지 않습니다.

## 7일 · 객체와 테스트로 기능 만들기

### 만들 기능

- `CollectionItem`에 `id`, `name`, `price`를 둡니다. `name`은 선택한 소장품 이름, `price`는 원 단위 정수 가격입니다.
- 이름 앞뒤 공백은 제거합니다. 이름이 없거나 공백뿐인 경우와 음수 가격은 거부합니다. 가격 0원은 허용합니다.
- 소장품 등록, 전체 목록 조회, 실제 등록한 id의 단건 조회를 구현합니다.
- `CollectionItemRepository` 인터페이스와 메모리 구현을 만들고, Service는 인터페이스를 생성자로 받습니다.
- 저장소가 id를 부여합니다. 조회할 때는 등록 결과의 실제 id를 사용합니다. id가 연속이거나 항상 1부터 시작한다고 가정하지 않습니다.
- 목록이 비어 있으면 빈 목록을 반환합니다. 없는 id의 단건 조회는 찾을 수 없다는 예외로 구분합니다.

### 완료 확인

| 입력·행동 | 확인할 결과 |
| --- | --- |
| 이름 `  노트  `, 가격 3000으로 등록 | 저장된 이름은 `노트`, 가격은 3000 |
| 등록 결과의 id로 조회 | 같은 소장품의 id·이름·가격 |
| 데이터가 없는 저장소에서 목록 조회 | 빈 목록 |
| 이름이 공백뿐이거나 가격이 -1 | 예외 발생, 저장된 목록은 그대로 |
| 가격 0으로 등록 | 정상 등록 |

등록·조회 성공, 빈 이름 거부, 음수 가격 거부를 포함한 단위 테스트를 최소 3개 작성합니다. 테스트마다 새 메모리 저장소를 사용합니다. HTTP 서버·Controller·JSON·DB·프론트엔드는 이날 요구하지 않습니다.

빠르게 끝났다면 가격 상한으로 목록을 찾는 기능을 선택해 추가하세요. 기존 목록이 변경되지 않는지도 테스트합니다.

## 14일 · 같은 프로젝트를 REST CRUD로 확장하기

7일에 만든 객체·Service·메모리 저장소를 유지하면서 Controller와 요청·응답 DTO를 연결합니다. 교재의 상품 API를 참고하고 경로는 `/items`를 사용합니다.

| 요청 | 성공 기준 | 실패 기준 |
| --- | --- | --- |
| `POST /items` | 201, 생성된 소장품 JSON, 실제 id를 가리키는 `Location` | 잘못된 이름·가격은 400 |
| `GET /items` | 200, 소장품 JSON 목록, 비어 있으면 `[]` | — |
| `GET /items/{id}` | 200, 해당 소장품 JSON | 없는 id는 404 |
| `PUT /items/{id}` | 200, 이름·가격을 바꾼 소장품 JSON, 기존 id 유지 | 없는 id는 404, 잘못된 이름·가격은 400 |
| `DELETE /items/{id}` | 204, 응답 본문 없음 | 없는 id는 404 |

요청 본문은 `name`, `price`를 사용합니다. 가격 누락·`null`·음수, 이름 누락·공백은 거부합니다. 실패한 등록·수정 후에는 기존 데이터가 바뀌지 않아야 합니다. 이 규칙을 확인할 때 없는 id와 잘못된 입력을 동시에 섞지 말고 각각 따로 요청합니다.

단건 응답은 `id`, `name`, `price`를 포함합니다. 목록의 순서는 직접 정하고 README에 기록하세요. API를 확인할 때 id 상수를 외우지 말고 실제 생성한 id를 사용합니다. 메모리 저장소이므로 서버를 다시 실행하면 데이터가 사라져도 됩니다.

등록 → 목록·단건 조회 → 수정 → 삭제 → 삭제한 id의 404를 직접 확인합니다. 기존 단위 테스트를 유지하고 수정·삭제·실패 후 데이터 보존 테스트를 추가합니다. 상태 코드·응답 본문·실패 전후 값을 README에 기록합니다. JPA·DB·로그인·프론트엔드는 필수가 아닙니다.

7일 코어가 미완료라면 먼저 등록·조회와 테스트를 복구하세요. 14일에는 동작하는 한 경로부터 연결하고, 미완료 이유와 다음 작업도 발표할 수 있습니다. 완성 범위를 부풀리거나 참고 코드의 예상 결과를 본인의 실행 결과로 제출하지 않습니다.

## 주말마다 개인 과제·발표 4교시

각 교시는 활동 45분과 휴식·정리 15분입니다. 개인 활동 4교시는 구현·발표 준비 105분, 발표·질문 75분, 휴식·정리 60분으로 총 4시간입니다. 점심은 별도입니다.

| 개인 활동 블록 | 활동 45분 | 휴식·정리 |
| --- | --- | --- |
| 1 | 구현 45분 | 15분 |
| 2 | 구현·테스트 45분 | 15분 |
| 3 | 마무리·발표 준비 15분 + 앞 5명 발표·질문 30분 | 15분 |
| 4 | 뒤 6명 발표·질문 36분 + 공통 피드백 9분 | 15분 |

11명 모두 개인 발표 4분과 질문 2분을 사용합니다. 별도 발표용 PPT는 만들지 않습니다. 코드·테스트·실행 화면을 미리 열어두세요.

발표에서는 주제와 구현 범위, 실제 성공·실패 결과, Controller/Service/Repository/Domain 중 해당하는 역할, 해결한 문제 또는 막힌 지점을 보여줍니다. 7일 발표에는 아직 만들지 않은 Controller나 HTTP 응답을 요구하지 않습니다.

7일은 책 학습 1~4교시 뒤 5~8교시에, 14일은 책 CRUD 학습 1~2교시 뒤 3~6교시에 개인 활동을 진행합니다. 14일 7~8교시는 DB 기초·JPA 입문을 위한 별도 시간입니다.
