# 개인 프로젝트 · 취미 위시리스트와 예산 추천

구매하거나 체험하고 싶은 책·게임·운동용품·캠핑 장비 등을 관리하는 개인 프로젝트입니다. 주제와 서비스 이름은 각자 정합니다. 등록·조회뿐 아니라 내 예산으로 고를 수 있는 항목을 추천하는 기능을 만듭니다.

책의 `product-api/`는 이후 수업에서 계속 사용합니다. 개인 코드는 같은 `sesac-spring-boot-study` 저장소의 `personal-project/`에 작성하고 기존 프로젝트는 보존합니다. 아래 조건은 교재 원문을 옮긴 것이 아니라 배운 내용을 적용하기 위한 과제 요구사항입니다.

## 수업 내용

- CH 09 상품 관리와 CH 12 객체지향·테스트 설명은 책으로 진행합니다.
- 책에서 본 객체의 규칙, 저장소의 추상화, 생성자 주입, 테스트를 개인 프로젝트에 적용합니다.
- 구현 및 준비 시간은 **150분**입니다.
- 결과 발표에서는 코드·테스트·실행 화면을 사용합니다. 발표용 PPT는 만들지 않습니다.

## 7일 기본 요구사항

### 데이터

`CollectionItem`에 `id`, `name`, `price`를 둡니다. `name`은 위시리스트 항목 이름, `price`는 원 단위 정수 가격입니다.

- 이름이 `null`이거나 비어 있거나 공백뿐이면 거부합니다. 저장할 때 이름 앞뒤 공백을 제거합니다.
- 가격은 0 이상입니다. 무료 항목도 등록할 수 있습니다.
- id는 프로그램에서 부여하고 조회할 때 실제 등록 결과의 id를 사용합니다. 번호의 연속성은 가정하지 않습니다.

### 기능

| 기능 | 요구사항 |
| --- | --- |
| 등록 | 이름과 가격을 받아 항목 저장 |
| 목록 조회 | 전체 항목 반환, 데이터가 없으면 빈 목록 |
| 단건 조회 | id로 항목 조회, 없는 id는 예외로 구분 |
| 예산 추천 | 각 항목의 가격이 예산 이하인 구매 후보를 가격 오름차순으로 최대 3개 반환 |

가격이 같은 항목은 등록 순서대로 추천합니다. 예산 0이면 무료 항목만 추천하고, 음수 예산은 거부합니다. 추천할 항목이 없으면 빈 목록을 반환합니다. 조회·추천으로 원본 데이터나 전체 목록의 순서가 바뀌면 안 됩니다.

### 추천 예시

아래 순서로 등록했다고 가정합니다.

| 항목 | 가격 |
| --- | ---: |
| 노트 | 12000 |
| 무료 샘플 | 0 |
| 펜 | 5000 |
| 스티커 | 5000 |
| 게임 | 8000 |

- 예산 5000 → 무료 샘플, 펜, 스티커
- 예산 0 → 무료 샘플
- 음수 예산 → 예외
- 항목이 없는 저장소 → 빈 목록

## 구조와 테스트

- Domain 객체가 이름·가격의 규칙을 지킵니다.
- Repository 인터페이스와 메모리 구현을 분리합니다. 저장·조회 코드는 저장소가 맡습니다.
- Service가 등록·조회·추천을 처리하고, Repository 인터페이스를 생성자로 받습니다.
- Spring이 Service와 Repository를 생성·연결한 결과를 실제로 확인합니다. 웹 서버 없이 컨텍스트 테스트로 확인해도 됩니다.
- 단위 테스트는 Spring 없이 새 저장소를 전달해 실행하고 테스트 간 데이터가 섞이지 않게 합니다.

최소 4개의 단위 테스트를 작성합니다. 정상 등록·조회, 잘못된 이름·가격, 추천 경계·정렬·최대 개수, 빈 결과·원본 보존을 확인합니다. 기대값과 실제 결과를 비교하고, 단순히 예외 없이 실행된 것만으로 성공이라고 기록하지 않습니다.

기본 과제에는 HTTP 서버·DB·프론트엔드가 필요하지 않습니다. 정답 코드 대신 책과 본인이 작성한 코드·테스트를 사용합니다.

- 프롬프트와 화면 디자인은 자율입니다. 생성된 코드를 직접 실행하고 수정한 내용을 설명합니다.

- API를 추가했다면 Controller는 요청·응답을, Service는 업무 처리를 맡습니다. 경로·입력·응답 계약을 README에 적고 실제 네트워크 요청과 결과를 확인합니다.
- 백엔드 핵심 로직은 직접 구현합니다. 화면에서만 데이터를 바꾸고 서버에도 저장됐다고 설명하지 않습니다.

## 9일 과제 · 위시리스트 구매 계획

기존 개인 Fork의 `personal-project/`에 위시리스트 항목을 묶어 구매 계획을 만드는 기능을 추가합니다. 먼저 자신의 PR에서 발견한 입력 검증·오류 응답·실패 시 데이터 보존 문제를 보완합니다. 기존 항목 등록·조회·추천 기능과 테스트는 유지합니다. 새 프로젝트·DB·외부 라이브러리는 필수가 아닙니다.

**1·2단계는 필수, 3단계는 추가 도전입니다.** 수업 중 공통 목표는 1단계까지이며, 필수 제출 범위의 마감은 별도로 안내합니다.

### 1단계 · 총예산 안에서 구매 계획 만들기

예산과 선택한 항목 id 목록을 받아 구매 계획을 생성하고, 생성한 실제 계획 id로 조회할 수 있게 합니다.

- 예산은 누락·`null`·음수를 거부하고 0은 허용합니다.
- 선택 목록은 누락·`null`·빈 목록을 거부합니다. 서로 다른 항목을 1~3개 선택해야 하며 중복 id·`null` id·없는 항목 id는 거부합니다. 0원 항목도 선택할 수 있습니다.
- 서버가 선택한 항목의 가격을 합산합니다. **총액이 예산 이하일 때만** 생성하며, 금액 합산과 남은 예산 계산에는 `long`을 사용합니다.
- 프로그램이 계획 id를 부여합니다. 결과에는 예산, 선택한 항목의 id·이름·가격, 총액, 남은 예산, `DRAFT` 상태를 포함합니다. id의 시작값이나 연속성은 가정하지 않습니다.
- 생성 시 항목의 이름·가격을 복사해 계획에 보관합니다. 이후 원본 위시리스트 항목의 이름·가격이 바뀌거나 삭제돼도 기존 계획 내용은 바뀌지 않아야 합니다.
- 생성에 실패하면 계획을 저장하지 않습니다. 없는 계획 id 조회는 찾을 수 없다는 오류로 구분합니다.

기존 추천은 개별 항목의 가격이 예산 이하인지 판단합니다. 이번 계획 생성은 **선택한 항목의 가격 합계**가 예산 이하인지 판단하는 별도 기능입니다.

### 2단계 · 구매 계획 수정·확정·취소

계획의 상태를 `DRAFT`(작성 중), `CONFIRMED`(확정), `CANCELLED`(취소)로 관리합니다.

| 현재 상태 | 허용할 작업 | 작업 후 상태 |
| --- | --- | --- |
| `DRAFT` | 예산·선택 항목 수정 | `DRAFT` |
| `DRAFT` | 확정 | `CONFIRMED` |
| `DRAFT` | 취소 | `CANCELLED` |

- 수정은 1단계의 입력·합계 조건을 모두 다시 만족해야 합니다. 수정 시점에 항목이 존재해야 하며, 성공하면 그 시점의 이름·가격을 새로 복사하고 총액·남은 예산을 계산합니다.
- 확정은 계획에 저장한 항목과 금액을 기준으로 처리합니다. 원본 위시리스트의 현재 가격으로 다시 계산하지 않습니다.
- 확정·취소된 계획의 수정, 재확정·재취소, 확정된 계획의 취소, 취소된 계획의 확정은 거부합니다.
- 없는 계획이나 허용되지 않은 작업은 이유를 구분해 응답합니다. 실패한 수정·상태 변경은 **기존 예산·항목·총액·남은 예산·상태를 모두 그대로 유지**해야 합니다.

실제 결제·재고 관리·주문 잠금은 요구하지 않습니다. 금액과 상태를 가진 구매 계획을 안전하게 변경하는 것이 목표입니다.

### 3단계 · 예산을 가장 알차게 쓰는 조합 추천

위시리스트에서 서로 다른 항목 1~3개를 골라, 총액이 예산을 넘지 않으면서 **가장 큰 총액의 조합**을 추천합니다. 기존의 개별 항목 추천은 변경하지 않습니다.

- 추천 대상 항목은 최대 20개입니다. 대상을 임의로 잘라내지 말고, 20개를 초과하면 명확한 오류로 거부합니다.
- 예산은 1단계와 같은 규칙을 적용합니다. 조건을 만족하는 조합이 없으면 빈 목록을 반환하며, 예산 0에서 무료 항목을 고르는 조합도 허용합니다.
- 총액이 같은 조합이 여러 개라면 선택 기준을 직접 정합니다. 같은 입력에는 같은 결과가 나오도록 하고 기준을 README에 기록합니다.
- 항목 가격이 6,000원·5,000원·4,000원이고 예산이 9,000원이면 5,000원과 4,000원의 조합을 찾아야 합니다.

### 설계와 QA

API 경로와 요청·응답 형식은 직접 정해 README에 기록합니다. Controller는 HTTP 입력·응답과 DTO 검증을, 구매 계획 도메인은 상태와 유효한 데이터 규칙을, Service는 항목 조회와 계획 생성·변경의 흐름을 담당하도록 나눕니다. 저장은 Repository 인터페이스와 메모리 구현으로 분리하고 생성자로 주입합니다.

정상 동작·잘못된 입력·경계 조건·실패 후 데이터 보존·계획에 복사한 값의 보존을 고려해 **직접 QA 체크리스트를 작성**합니다. 확인 순서와 입력값은 직접 정하고 실행 결과를 기록합니다. 기존 테스트를 보존하며, 합계 계산·상태 변경 규칙·실패 후 데이터 보존·계획에 복사한 값의 보존을 확인하는 의미 있는 테스트를 추가합니다. 프론트엔드는 필수가 아닙니다.

README에는 API 계약, 금액 계산과 상태 변경 규칙, 클래스별 책임, QA·테스트 결과, 발견한 문제와 수정 내용, 단계별 완료·미완료 범위를 적습니다. 추가 도전을 했다면 동일 총액 조합의 선택 기준도 포함합니다.

### 제출

기존 구현이 있는 브랜치에서 새 작업 브랜치를 만들며 이름은 자율입니다. 개인 Fork의 `origin`에 Push하고 공용 저장소 `sesac-ddm-4-web/sesac-spring-boot-study`에 **`[11/09][이름] 위시리스트 구매 계획` Issue 1개·PR 1개**로 코드·테스트·README를 제출합니다. 검증 보완과 구매 계획을 함께 기록하므로 별도의 유효성 검사 과제 PR은 요구하지 않습니다. 상품 API의 수업 중 QA 기록은 별도 학습 기록입니다.

PR의 base는 조직 원본의 `main`, head는 본인 Fork의 작업 브랜치로 선택합니다. 본문에 이전 PR 링크와 이번 변경 범위를 적고, 리뷰 수정은 같은 브랜치에 Push합니다. 강사가 확인 후 병합 없이 PR·Issue를 닫습니다. 제출 브랜치는 보존합니다.

## 14일 확장

같은 개인 프로젝트에 책에서 배운 REST CRUD·입력 검증·예외 처리를 적용합니다. 7일의 추천 기능과 테스트는 유지합니다.

| 요청 | 성공 | 실패 |
| --- | --- | --- |
| `POST /items` | 201, 생성된 항목 JSON과 `Location` | 잘못된 이름·가격 400 |
| `GET /items` | 200, 목록 JSON, 없으면 `[]` | — |
| `GET /items/{id}` | 200, 항목 JSON | 없는 id 404 |
| `PUT /items/{id}` | 200, 수정된 항목 JSON, id 유지 | 없는 id 404, 잘못된 이름·가격 400 |
| `DELETE /items/{id}` | 204, 본문 없음 | 없는 id 404 |

요청은 `name`, `price`, 단건 응답은 `id`, `name`, `price`를 사용합니다. 이름 누락·공백과 가격 누락·`null`·음수를 거부하고 실패 전후 데이터가 유지되는지 확인합니다. 없는 id와 잘못된 입력은 각각 따로 테스트합니다.

추천을 API로 제공하는 것은 선택입니다. 예를 들어 `GET /items/recommendations?budget=5000`을 추가할 수 있으며, 경로와 응답은 README에 명시합니다. 메모리 저장소이므로 재시작 후 데이터가 사라져도 됩니다. JPA·DB·로그인·프론트는 기본 요구가 아닙니다.

구현 및 준비는 150분입니다. 미완료라면 동작하는 한 기능과 막힌 원인·다음 작업도 발표합니다.
