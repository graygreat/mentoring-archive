# 2026-11-12 · 교재 CH 11과 DB 연동

## 진행 범위

4시간 동안 교재 CH 11의 DB 사용 웹 애플리케이션, DB 다뤄 보기, 상품 추가, 조회·수정·삭제를 함께 읽습니다. 코드 설명은 책으로 대체하고 교육생이 기존 `product-api/`에 직접 적용합니다. 강사 코딩 시연이나 새 프로젝트 생성은 하지 않습니다. 책에서 사용하는 JDBC 접근 방식을 확인하며 특정 API를 책의 구현이라고 단정하지 않습니다. 이후 `personal-project/` 위시리스트 DB 연동을 필수로 진행하고 완료자는 장바구니 영속화로 확장합니다.

## 설정 확인

기존 Java 17·Spring Boot 4·Gradle 프로젝트를 유지합니다. 필요한 경우 `implementation 'org.springframework.boot:spring-boot-starter-jdbc'`와 `runtimeOnly 'com.h2database:h2'`를 추가하고 버전은 Spring Boot 의존성 관리를 따릅니다. 기존 의존성을 무작정 교체하지 않습니다.

상품 앱은 `jdbc:h2:file:./data/products`, 개인 앱은 `jdbc:h2:file:./data/wishlist`로 분리합니다. Spring Boot 공식 문서의 권장대로 파일 URL에 `;DB_CLOSE_ON_EXIT=FALSE`를 덧붙일 수 있습니다. `spring.datasource.url`, `spring.datasource.username`, `spring.datasource.password`를 실제 설정과 맞추고 비밀값은 제출하지 않습니다. 상대 파일 경로는 실행 작업 디렉터리에 따라 달라집니다.

독립 SQL 연습의 `jdbc:h2:mem:db_basics`는 마지막 연결/프로세스 종료 시 사라지는 연습용입니다. 영구 저장 확인은 앱 파일 DB를 같은 URL·작업 디렉터리에서 재시작해 수행합니다. 테스트는 별도 DB를 사용합니다.

책의 테이블 SQL이나 비파괴 `CREATE TABLE IF NOT EXISTS`로 준비합니다. classpath `schema.sql`을 파일 DB에서 자동 실행하려면 `spring.sql.init.mode=always` 등 실행 조건을 확인해야 합니다. 시작할 때 DROP·TRUNCATE하거나 고정 seed를 반복 삽입하지 않습니다. JPA `ddl-auto`를 JDBC 테이블 생성 설정으로 넣지 않습니다.

공식 문서: [Spring Boot SQL](https://docs.spring.io/spring-boot/reference/data/sql.html), [DB 초기화](https://docs.spring.io/spring-boot/how-to/data-initialization.html), [H2 URL](https://h2database.com/html/features.html#database_url).

## 구현과 확인

Repository 인터페이스, Service, Domain, DTO와 HTTP 계약을 유지합니다. 실행 시 Memory/DB 구현 중 하나만 주입되도록 선택합니다. DB가 발급한 키로 생성 결과를 만들고 조회 복원에서도 그 id를 보존합니다. `AtomicLong`이나 `MAX(id)+1`로 DB id를 대신 발급하지 않습니다. 없는 id UPDATE·DELETE는 영향받은 행 수 0을 확인해 404로 변환합니다.

위시리스트의 수동/외부 필드와 저장한 메타데이터를 유지합니다. NULL과 0, 외부 식별자와 로컬 id를 구분합니다. 수동 상품의 이름 중복은 허용하고 name에 새 UNIQUE 제약을 강제하지 않습니다. SQL 입력은 문자열 이어 붙이기 대신 책의 파라미터 바인딩 방식을 따릅니다. 외부 식별자 조합의 UNIQUE 제약과 409 변환을 적용하되 모든 DB 예외를 409로 덮지 않습니다. 목록 순서는 ORDER BY로 명시하고 동률의 등록 순서, 가격 0, 추천·검증·쿠폰 등 기존 동작을 유지합니다. 실패 응답만으로 DB 롤백이 된다고 설명하지 않습니다.

장바구니 확장은 저장된 행 id·수량·이름·단가·재고 복사본을 유지합니다. 원본 변경/삭제가 복사본을 바꾸지 않으며 FK CASCADE로 장바구니를 지우거나 RESTRICT로 원본 삭제를 막지 않도록 설계합니다. 성공 응답뿐 아니라 DB 실제 행과 같은 설정의 재시작 후 동일 id·값도 확인합니다. 쿠폰 선택과 미리보기 상태는 추가 저장하지 않습니다. 여러 쓰기가 하나의 작업을 이루면 중간 실패 시 부분 저장이 남지 않도록 책 수준에서 트랜잭션 범위를 확인합니다.

QA 체크리스트는 교육생이 작성하고 정상·실패·재시작 실제 결과를 기록합니다. Repository 통합 테스트는 별도 DB에서 실행하고 기존 단위 테스트는 유지합니다. 상세 정답 QA 시나리오나 DB 완성 코드는 배포하지 않습니다. 마지막 파일 버튼 3개는 기존 HTTP 검증·예외 처리 보충 코드입니다.

## 슬라이드별 확인 사항

### 1. 데이터베이스 연동

책과 실제 구현을 함께 확인합니다.

### 2. 수업 내용

4시간 수업입니다. 책 읽기와 교육생 직접 구현을 오가며 진행하고 강사 코딩 시연은 하지 않습니다. 책의 상품 관리 애플리케이션이 기준이며 기존 Java 17·Spring Boot 4 프로젝트를 이어갑니다.

### 3. 책에서 함께 읽을 부분

판본별 쪽수는 책에서 확인합니다. 교재에서 사용하는 JDBC 접근 방식과 설정을 직접 읽고 따릅니다. 책 원문을 확인하지 않은 특정 JDBC API를 교재 방식이라고 단정하지 않습니다. 오늘 JPA로 바꾸거나 새 프로젝트를 만들지 않습니다.

### 4. Java 객체·JSON·DB 행

책과 실제 구현을 함께 확인합니다.

### 5. 테이블·행·열·기본 키

책과 실제 구현을 함께 확인합니다.

### 6. 자료형과 NULL

필수 name·price는 기존 입력과 도메인 검증을 유지합니다. 외부 상품 메타데이터처럼 값이 없는 것이 허용되는 열은 별도로 결정합니다. 수동 상품의 외부 id가 NULL일 수 있으므로 외부 식별자 중복 제약과 함께 설계합니다.

### 7. SQL 네 가지 작업

각 SQL은 교재의 상품 테이블을 보며 읽습니다. 상세 SQL 완성 답안을 배포하지 않고 테이블과 SQL은 교육생이 설계합니다. 조건 없는 UPDATE·DELETE가 여러 행에 영향을 주는 이유를 확인합니다.

### 8. 메모리 대신 DB에 저장

기존 Map의 항목이 DB로 자동 이관되지는 않습니다. 필수 검증은 DB 전환 후 API로 저장한 데이터가 실제 DB 행과 재시작 후에도 남는지입니다. 기존 기능과 테스트의 동작 계약을 보존하며 메모리 항목 자동 이관을 요구하지 않습니다. 기존 메모리 저장 구현은 보존할 수 있지만 실행 시 실제 사용할 Repository 빈은 메모리 또는 DB 중 하나만 선택합니다. 두 구현을 모두 자동 등록해 주입이 모호해지지 않도록 책의 설정 방식에 맞춰 구성합니다.

### 9. 앱 DB와 SQL 연습 DB 구분

DB 드라이버와 JDBC 접근에 필요한 의존성을 기존 build.gradle에 추가합니다. 임의의 별도 버전을 섞지 않고 프로젝트 Spring Boot의 의존성 관리를 따릅니다. 메모리 H2는 영구 저장 확인에 사용하지 않습니다. 파일 URL은 실행 작업 디렉터리를 기준으로 하므로 프로젝트와 실행 위치를 함께 기록합니다.

### 10. 재시작해도 같은 DB 사용

schema.sql 등 초기화 기능을 선택하면 실제 실행 조건과 기존 테이블이 있을 때의 동작을 확인합니다. 실행마다 전체 삭제·고정 id 재삽입을 하지 않습니다. 파일 DB 경로를 바꾼 뒤 데이터가 사라졌다고 오해하지 않도록 URL과 작업 디렉터리를 확인합니다. 테스트는 앱 파일 DB와 분리합니다.

### 11. DB가 만든 id를 사용

생성 결과의 실제 DB id를 응답과 Location에 사용합니다. 조회할 때 신규 생성용 생성자를 그대로 써 id를 재발급하지 않도록 복원 경로를 구분합니다. Domain 규칙을 우회하지 않되 DB 행의 식별자는 보존합니다.

### 12. 기존 인터페이스로 DB 구현 연결

수업에서는 기존 클래스 책임을 유지하면서 저장 방식만 바꿉니다. JDBC 접근 코드는 책의 구현을 참고합니다. 메모리 Repository를 삭제해야만 DB 구현을 사용할 수 있는 것은 아니며 실행 설정으로 한 구현을 선택할 수 있습니다.

### 13. 상품 API를 DB에 연결

책과 기존 API의 필드·생성자·메서드가 다르면 자신의 코드에 맞춰 적용합니다. 기존 정상·실패 동작을 바꾸는 기능 추가가 아니라 저장 구현 전환입니다. 가격 0, 입력 누락/null, 없는 id의 HTTP 계약을 유지합니다.

### 14. 실패한 요청은 DB도 그대로

SQL 실행 결과의 affected rows를 확인합니다. UPDATE·DELETE가 예외 없이 끝나도 대상이 없을 수 있습니다. 여러 쓰기가 한 작업을 이루면 트랜잭션이 필요할 수 있으며 HTTP 상태 변환과 DB 트랜잭션은 서로 다른 책임입니다. 구체 설정은 교재와 사용 중인 JDBC 방식에 맞춰 확인합니다.

### 15. 과제

책과 실제 구현을 함께 확인합니다.

### 16. 기존 위시리스트를 DB에 저장

실제 필드 이름은 기존 구현에 따릅니다. 기존 외부 이미지 필드가 thumbnail이면 임의로 image로 바꾸도록 강제하지 않습니다. 9일 선택 기능을 모두 끝내지 못한 교육생은 위시리스트 DB 연동을 먼저 완료한 뒤 미완료 기능을 이어갑니다. 수동 상품과 외부 상품을 모두 복원할 수 있게 설계합니다.

### 17. 기존 API와 추천 규칙 유지

DB의 기본 반환 순서는 보장된 등록 순서가 아닙니다. id 또는 생성 순서 필드 등 실제 설계한 기준과 정렬 방향을 명시하고 동률 처리까지 기존 계약과 맞춥니다. 구현되지 않은 추가 추천 기능을 새로 필수로 만들지는 않습니다.

### 18. 외부 상품 식별자와 중복 처리

애플리케이션의 사전 중복 검사만으로 DB 중복 제약을 대체하지 않습니다. DB 유니크 위반 중 외부 상품 식별자 충돌에 해당하는 것을 기존 409 계약으로 변환하고 모든 DB 오류를 409로 덮지 않습니다. 수동 상품의 외부 식별자 NULL 처리와 DB 유니크 제약을 함께 검토합니다. 외부 호출·쿠폰·추천·검증 기능을 제거하지 않습니다.

### 19. 장바구니도 DB에 저장

위시리스트 DB 연동을 끝낸 교육생이 진행합니다. 원본 상품이 삭제되어도 장바구니 줄과 처음 저장한 단가·재고가 유지돼야 합니다. 원본 변경을 조회 시 자동 반영하는 조인만으로 스냅샷을 대신하지 않습니다. FK의 ON DELETE CASCADE로 장바구니를 함께 지우거나 RESTRICT로 원본 삭제를 막아 기존 계약을 바꾸지 않습니다. 스냅샷과 원본 관계를 분리하거나 삭제 시 관계만 해제하는 등 자신의 DB 구조에 맞게 설계합니다. 중복 담기·수량 변경·삭제 후 다시 담기의 기존 복사 규칙을 유지합니다.

### 20. 여러 쓰기는 함께 성공하거나 취소

예를 들어 한 업무가 여러 행을 함께 변경한다면 전체 성공 또는 전체 취소가 필요합니다. 트랜잭션의 구체 API를 새 강의로 확장하지 않고 교재 수준에서 적용 범위를 확인합니다. 쿠폰 미리보기처럼 읽기 계산만 하는 작업에 저장 상태를 새로 만들지 않습니다. 예외를 잡아 HTTP 400으로 바꾸는 것 자체가 롤백 설정은 아닙니다.

### 21. 직접 확인할 항목 작성

상세 정답 체크리스트를 대신 배포하지 않습니다. 의미 있는 DB 통합 테스트로 실제 저장·조회·수정·삭제와 id 보존을 검증합니다. 테스트 전용 DB·URL을 사용해 앱 데이터를 오염시키지 않습니다. 단순 모의 Repository 호출 검증만으로 SQL 동작을 확인했다고 하지 않습니다. 재시작 검증은 같은 파일 URL과 작업 디렉터리로 실제 수행합니다.

### 22. 적용한 내용을 설명하기

발표 전에 자기 코드와 DB를 근거로 확인합니다. 화면에 체크 표시만 적는 것이 아니라 SQL·복원 코드·실행 결과로 설명하도록 합니다.

### 23. DB 연동 결과 제출

base는 조직 원본 sesac-ddm-4-web/sesac-spring-boot-study의 main, head는 개인 Fork의 작업 브랜치입니다. 개인 origin으로 Push합니다. 원본 main을 받아 자신의 지난 구현을 대체하지 않습니다. 강사는 병합 없이 PR·Issue를 닫고 교육생의 작업 브랜치는 보존합니다. 실제 DB 데이터 파일·비밀값·build/.gradle/IDE 파일을 제출하지 않고 실행 가능한 소스와 Gradle Wrapper는 유지합니다. 필수 PR을 둘로 나누거나 자가 병합하도록 요구하지 않습니다.

### 24. 14일 · 단축 URL·주문 API·JPA

먼저 책의 과제 요구사항을 확인한 뒤 풀이 코드와 완성 예제는 최대한 보지 않고 개인별로 구현합니다. 기존 상품·위시리스트 DB 연동 결과는 보존합니다. 두 과제의 필수 구현에 새 JPA 전환을 추가하지 않으며, JPA는 다음 주에 이어 학습합니다.

### 25. 교재와 공식 문서

JDBC·H2 설정은 현재 프로젝트 버전과 공식 문서를 확인합니다. 참고 파일은 기존의 입력 DTO·Controller·예외 핸들러이며 오늘 DB 구현 코드를 제공하는 파일이 아닙니다. 파일 이름 버튼은 기존 HTTP 검증·예외 처리의 전체 보충 코드를 엽니다. DB 연동 구현은 교재를 읽고 직접 작성합니다.
