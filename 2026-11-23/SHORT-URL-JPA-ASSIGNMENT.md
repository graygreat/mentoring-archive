# 나만의 단축 URL 서비스 JPA 전환

지금까지 만든 **본인의 단축 URL 서비스**에서 저장 방식을 JPA로 교체한다. 새 서비스를 처음부터 만드는 과제가 아니다. 외부에서 보이는 기능은 유지하면서 데이터 저장과 트랜잭션 경계를 바꾸는 것이 목표다.

## 유지할 것과 바꿀 것

| 유지할 것 | 바꿀 것 |
|---|---|
| 기존 URL 생성·리다이렉트 기능 | 메모리·JDBC 등 기존 데이터 접근을 JPA로 교체 |
| 기존 요청·응답·상태 코드와 프론트 연결 | Entity 매핑과 Spring Data Repository 사용 |
| 입력 검증과 없는 코드 처리 | Service의 쓰기 트랜잭션 경계 명시 |
| 이미 구현한 통계·만료·관리 등 본인 기능 | 파일·서버 DB에 데이터를 보존하는 설정 |

기존에 구현하지 않은 통계·어드민·수정·삭제 기능을 이번 기본 과제 때문에 모두 새로 만들 필요는 없다. 기존 코드와 데이터는 임의로 삭제하지 않는다. JPA를 이미 사용하고 있다면 트랜잭션 경계, 고유 제약조건, 재시작 보존과 실패 복구를 점검하고 근거를 보완한다.

## 기존 동작부터 기록한다

수정 전에 본인 서비스의 API 목록과 사용 중인 저장소를 확인한다. 프론트가 호출하는 주소·메서드·요청과 응답 형식도 확인한다. 서비스 실행 방법, 실행 폴더, DB 주소와 프로파일을 기록한다. 실제 비밀번호는 기록하지 않는다.

먼저 현재 동작하는 기능을 확인하고, **본인이 QA 체크리스트를 작성한다.** 정상 입력뿐 아니라 잘못된 입력, 존재하지 않는 코드, 중복 가능성, 이미 구현한 부가 기능을 포함해 어떤 결과를 기대하는지 적는다. 다른 교육생의 체크리스트를 그대로 복사하지 말고 본인 기능에 맞춘다.

## Entity와 저장소를 연결한다

- 저장할 필드와 DB 열을 대응시킨다. ID 필드에 `@Id`를 지정하고, 자동 생성한다면 프로젝트의 DB와 맞는 생성 전략을 사용한다. 새 ID가 1부터 시작하거나 연속이라고 가정하지 않는다.
- 단축 코드는 DB의 고유 제약조건으로 중복을 막는다. 코드 생성 전에 조회하는 검사만으로 동시 요청의 중복을 막을 수는 없다. 기존 스키마라면 애너테이션 추가만으로 제약조건이 반영되었다고 가정하지 말고 실제 스키마를 확인한다.
- Entity에는 JPA가 사용할 public 또는 protected 기본 생성자가 필요하다. 모든 필드의 public setter를 만들 필요는 없다.
- HTTP 요청·응답 DTO와 저장 Entity의 역할을 구분한다. Entity를 그대로 응답해 프론트 계약이나 지연 로딩에 의존하지 않도록 한다.
- Spring Data Repository를 연결한다. 기존 도메인 Repository 인터페이스가 있다면 JPA 어댑터를 구현해서 유지할 수 있다. 현재 구조에 맞춰 선택하고 이유를 설명한다.
- 기존 메모리·JDBC 구현을 보존할 수 있지만, 같은 역할의 빈이 의도치 않게 중복 등록되지 않게 한다. 실제 요청이 JPA 저장소를 사용하는지 확인한다.

## Service의 트랜잭션 범위를 정한다

쓰기 기능의 Service 메서드에 `org.springframework.transaction.annotation.Transactional`을 적용한다. Spring이 관리하는 빈을 외부에서 호출하는 기본 상황을 기준으로 동작을 확인한다. 단순히 모든 메서드에 붙이기보다 어느 작업을 하나의 성공·실패 단위로 묶었는지 설명한다.

- 기존 행을 수정할 때는 일반 쓰기 트랜잭션 안에서 엔티티를 조회하고 변경한다. 관리 엔티티의 변경 감지와 새 객체·분리 객체를 구분한다.
- 읽기만 하는 Service에는 `readOnly = true`를 사용할 수 있다. 읽기 전용 힌트이며 쓰기 차단을 보장하는 기능은 아니다.
- 리다이렉트할 때 클릭 수나 마지막 접근 시각을 함께 수정한다면 읽기 전용 작업이 아니다. 쓰기 범위로 설계한다. `clickCount++` 자체가 동시 요청에서도 안전한 원자적 증가인 것은 아니다.
- 기본 `REQUIRED`는 기존 트랜잭션이 있으면 참여한다. 내부 메서드의 정상 종료가 최종 commit이라는 뜻은 아니다. 기본 프록시의 자기 호출은 안쪽 메서드의 새 설정을 적용하지 않는다.
- DB rollback은 이미 보낸 이메일, 외부 HTTP 요청, 브라우저 이동까지 취소하지 않는다. DB에서 함께 취소할 수 있는 범위를 구분한다.

## 재시작 후에도 데이터를 보존한다

개발용 파일 DB 또는 별도 서버 DB를 사용한다. 개인 서비스의 보존 확인에는 메모리 DB나 `create`·`create-drop`처럼 데이터를 지울 수 있는 설정을 사용하지 않는다. 기존 데이터가 있다면 백업·스키마 변경·이관 필요성을 확인하고 계획을 기록한다. 기존 데이터를 지워서 전환이 끝난 것처럼 처리하지 않는다.

실행 폴더와 프로파일이 달라져 다른 파일 DB에 연결되지 않도록 한다. 파일 DB를 선택했다면 같은 위치의 DB 파일에 다시 연결되는지 확인한다. DB 파일·DB 계정 비밀번호·`.env`·빌드 결과는 Git에 올리지 않는다.

정상 요청으로 URL을 저장하고 commit된 뒤 애플리케이션을 종료한다. 같은 DB에 다시 연결해 기존 코드와 기존 동작을 사용할 수 있는지 확인한다. 단순히 같은 실행 안에서 엔티티의 필드를 읽은 결과만으로 영구 저장을 증명하지 않는다.

## 정상 commit과 실패 rollback을 비교한다

수동 실행 또는 이미 익숙한 테스트 방식으로 확인해도 된다. 이번 과제에서 새 테스트 코드를 반드시 작성하도록 요구하지 않는다.

1. 본인 서비스의 쓰기 작업을 고른다. 수정 기능이 있다면 저장된 링크의 값을 바꾸는 작업을 사용하고, 생성만 있다면 새 링크를 저장하는 작업을 사용한다.
2. 정상 완료한 경우 작업을 마친 뒤 **별도 트랜잭션에서 다시 조회**해 값이나 새 행이 남았는지 확인한다.
3. 별도 학습 데이터와 로컬 임시 코드에서 같은 작업의 SQL 반영 뒤 실패를 재현한다. 예를 들어 저장 또는 관리 객체 변경 후 `flush()`하고 `IllegalStateException`을 밖으로 전파한다. 반드시 Spring 프록시를 거친 쓰기 트랜잭션 안에서 실행한다.
4. 실패 요청이 끝난 뒤 새 트랜잭션에서 다시 조회한다. 수정한 값이 이전 값으로 남는지 또는 생성한 새 행이 없는지 확인한다. 강제 예외를 넣기 전·후 결과를 비교해 기록한다.
5. 같은 메모리 객체의 필드값만 확인하지 않는다. rollback은 Java 필드를 자동으로 되돌리지 않는다. `clear()`와 재조회는 같은 트랜잭션의 동기화 확인에는 쓸 수 있지만 commit 증거가 되지는 않는다.
6. 테스트 자체를 감싼 트랜잭션이 끝나지 않은 상태에서 조회했다면 실제 commit 확인과 구분한다. SQL 로그만으로 확정 여부를 판단하지 않는다.
7. 확인 후 강제 실패 코드와 임시 실패용 엔드포인트를 제거한다. 상시 접근 가능한 실패 기능을 결과물로 제출하지 않는다.

flush에서 제약조건 오류가 먼저 발생한 경우에는 그 원인을 구분해서 기록한다. 예외를 catch하고 정상 반환하면 별도 rollback-only 표시가 없는 한 commit될 수 있고, 이미 rollback-only가 되었다면 catch해도 최종 commit이 실패할 수 있다.

## QA 결과와 설명을 남긴다

본인이 작성한 QA 체크리스트를 전환 전·후에 실행한다. 본인 기능의 기대 결과, 실제 결과, 수정한 문제를 README 또는 PR에 기록한다. 체크리스트에는 API·프론트 계약 유지, 실제 JPA 저장소 사용, 재시작 보존, 정상 commit·실패 rollback을 설명할 수 있는 항목이 있어야 한다.

| 내가 확인할 상황 | 기대 결과 | 실제 결과·근거 | 수정·남은 문제 |
|---|---|---|---|
| 직접 작성 | | | |

완료 기준은 애너테이션을 붙인 코드가 있다는 것이 아니라, 기존 서비스가 동작하고 DB 보존과 실패 취소를 확인했으며 그 이유를 설명할 수 있는 것이다.

## 추가 과제

기본 전환과 QA를 마친 경우 선택한다. 순서대로 도전해도 되고, 이미 구현한 기능과 중복된다면 다른 항목을 선택해도 된다.

### 1단계 · 저장한 링크 찾기

본인 서비스의 사용 목적에 맞는 검색·정렬·페이지 조회를 추가한다. 제목·원본 URL 등의 검색 조건과 정렬 기준을 정하고, 페이지의 첫·마지막·결과 없음 상황을 본인의 QA에 포함한다. 조회 조건에 맞는 Repository 메서드나 쿼리를 선택한 이유를 설명한다.

### 2단계 · 변경 내역 함께 남기기

원본 URL·제목·만료 시각 등 실제로 수정할 필요가 있는 항목을 고른다. 수정 기능이 없다면 필요한 수정 동작을 추가한다. 링크 변경과 변경 이력을 **같은 DB 트랜잭션**에 저장한다. 중간 실패 시 둘 다 취소되는지 새 트랜잭션에서 확인한다. 무엇을 언제 어떤 값에서 어떤 값으로 바꿨는지 읽을 수 있게 한다.

### 3단계 · 동시에 요청해도 규칙 지키기

단축 코드 충돌 상황을 의도적으로 재현하고, DB 고유 제약조건 위반 시 사용자 응답 또는 재시도 정책을 정한다. 제약조건 오류로 실패한 트랜잭션 안에서 그대로 재시도하는 방식은 피하고 재시도 경계를 검토한다. 클릭 수가 있는 서비스라면 동시에 증가할 때 값이 유실되는지도 관찰하고 원자적 UPDATE나 잠금 등 대응 방식을 비교한다. 로그만 보지 말고 최종 DB 값으로 확인한다.

고급 기능을 추가하느라 기본 생성·리다이렉트 기능이나 데이터 보존을 깨뜨리지 않는다.

## AI 사용

백엔드는 최대한 직접 구현하되 AI의 도움을 받을 수 있다. 받은 코드가 무엇을 하는지, 트랜잭션이 어디서 시작하고 끝나는지, 실제 SQL과 결과를 본인이 설명한다.

기존 프론트는 유지하거나 AI로 보완할 수 있다. 순수 HTML·CSS·JavaScript만 사용하고 외부 라이브러리 CDN은 사용하지 않는다. 프롬프트는 자율적으로 작성한다. 특정 프롬프트 형식이나 대화 기록 전체 제출은 요구하지 않는다.

## GitHub 제출

공용 저장소는 [sesac-ddm-4-web/sesac-spring-boot-study](https://github.com/sesac-ddm-4-web/sesac-spring-boot-study)다.

1. 이미 사용 중인 본인 fork와 본인 프로젝트 폴더에서 이어서 작업한다. 별도 새 저장소나 새 개인 프로젝트를 만들 필요는 없다.
2. 브랜치 이름은 자율적으로 정한다. 기존 브랜치·PR에 이어서 작업한다면 이번 JPA 변경 범위를 구분한다.
3. 과제 추적은 공용 저장소 Issue에 남긴다. 새로 만든다면 제목은 `[과제] 이름 / 단축 URL JPA 전환`으로 작성한다. 기존 관련 Issue가 있으면 갱신·재사용할 수 있다.
4. 본인 fork에 push하고 공용 원본 저장소의 `main`을 대상으로 PR을 올린다. 새 PR 제목은 `[이름] 단축 URL 서비스 JPA 전환`으로 작성한다. 기존 관련 PR을 이어서 사용하는 것도 가능하다.
5. PR 본문에 관련 공용 Issue 링크, 저장소 교체 위치, 트랜잭션 경계, 실행 방법, QA 결과, 정상·실패 비교와 남은 문제를 적는다. 다른 저장소의 Issue와 연결할 때 단순 `#번호`만으로 잘못 연결하지 말고 정확한 링크를 사용한다.
6. 다른 교육생의 파일 변경이나 DB 파일·비밀번호·빌드 결과가 섞이지 않았는지 확인한다. 공용 원본 PR은 강사 검토를 받으며 본인이 임의로 병합하지 않는다.

마감은 별도 안내한다. 별도 문서 시스템이나 주문 조회 랩의 추가 제출은 요구하지 않는다.
