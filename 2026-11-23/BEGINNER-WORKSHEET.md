16일 자료의 [28쪽 · 트랜잭션 기본](../2026-11-16/#slide-28)부터 이어간다. 코드 복사나 독립 예제 프로젝트 실행 없이, 장표의 그림을 보고 결과를 예상한 뒤 자기 말로 설명한다. 마지막에는 [본인의 단축 URL 서비스 JPA 전환 과제](SHORT-URL-JPA-ASSIGNMENT.md)에 적용한다.

모르는 DB 용어는 [DB 기초](../shared/db-basics/)에서 확인한다. 설명용 상품은 키보드이고 가격을 30000원에서 25000원으로 변경한다. 설명용 ID를 실제 생성 ID로 가정하지 않는다.

## 부분 성공은 왜 문제일까?

장표에서 상품 가격 변경과 변경 이력 저장이 각각 어디에 있는지 찾는다. 둘은 하나의 기능에서 수행하는 서로 다른 DB 작업이라고 가정한다. 이력 기능은 설명을 위한 것이며 기본 과제로 새로 만들라는 뜻이 아니다.

| 그림에서 읽을 것 | 내 설명 |
|---|---|
| 가격 변경만 저장되고 이력은 실패하면 어떤 상태인가? | |
| 둘이 함께 성공하거나 함께 취소되어야 한다면 어디를 묶어야 하는가? | |
| 이 묶음의 변경 확정과 변경 취소를 각각 무엇이라고 하는가? | |

트랜잭션은 DB 작업의 성공·실패 단위를 정하는 데 사용한다. 모든 외부 행동까지 자동으로 되돌리는 기능은 아니다.

## Service와 프록시는 어디에 있을까?

그림의 호출 순서를 따라가며 세 대상을 찾는다.

- Service: 하나의 업무를 진행하는 애플리케이션 객체.
- Spring 빈: Spring이 만들고 연결해 관리하는 객체.
- 프록시: 실제 Service 호출 앞뒤에 트랜잭션 처리를 적용하는 대리 객체.

| 질문 | 그림의 위치·내 설명 |
|---|---|
| 호출이 실제 Service에 들어가기 전에 무엇을 거치는가? | |
| 정상 실행 뒤 변경을 확정하는 처리는 누가 앞뒤에서 적용하는가? | |
| 왜 Controller 요청 형식보다 Service의 업무 범위에 트랜잭션을 두는가? | |

기본 그림은 다른 객체에서 Spring 빈의 public Service 메서드를 프록시를 통해 호출하는 상황이다. 프록시는 별도 웹 서버가 아니다.

## 객체의 가격과 DB의 가격을 나눈다

상품 객체와 DB 행은 서로 다른 곳에 있다. 왼쪽 객체와 오른쪽 DB 중 지금 값이 바뀐 쪽을 장표에서 가리킨다.

| 시점 | Java 객체 | DB 상태 |
|---|---|---|
| 상품 조회 | 30000 | 30000 |
| 관리 객체의 가격 변경 | 25000 | SQL 반영 전이라면 30000 |
| flush | 25000 | 현재 트랜잭션에서는 25000, 아직 미확정 |
| commit을 선택 | 25000 | 25000으로 확정 |
| commit 대신 rollback을 선택 | 25000이 자동 복원되지 않음 | 기존 30000으로 변경 취소 |

마지막 두 행은 **서로 다른 두 갈래**다. commit한 다음 rollback으로 같은 변경을 되돌리는 순서가 아니다. 다른 트랜잭션에서 보이는 값은 격리 수준 등에 영향을 받는다.

## 왜 별도 save 없이 수정될 수 있을까?

장표의 관리 Entity, 조회 당시 값, 현재 값을 각각 찾는다. 일반 쓰기 트랜잭션 안에서 조회한 관리 Entity라는 조건을 붙여 설명한다.

| 그림에서 확인할 것 | 내 설명 |
|---|---|
| 조회 당시 가격과 현재 가격은 무엇이 다른가? | |
| 이 차이는 어떤 과정에서 DB 수정으로 이어지는가? | |
| new로 만들기만 한 객체에도 똑같이 적용되는가? | |
| 같은 컨텍스트에서 같은 ID를 다시 find하면 어떤 객체를 재사용할 수 있는가? | |

객체 필드가 바뀐 순간과 UPDATE 실행, 최종 commit은 구분한다. IDENTITY 전략에서는 ID를 얻기 위해 INSERT가 일찍 실행될 수 있지만 그 자체가 commit이라는 뜻은 아니다.

| 원본 URL 조회와 클릭 수 증가를 함께 수행 | | |

readOnly는 읽기 의도를 전달하는 힌트다. 쓰기를 확실히 차단하는 장치로 생각하지 않는다.

기본 rollback 규칙에서 RuntimeException·Error와 checked exception은 같지 않다. 장표에서 기본 규칙과 별도 설정이 필요한 경우를 구분한다. 예외가 발생했다는 사실뿐 아니라 어떤 예외가 트랜잭션 경계 밖으로 전파되었는지 확인해야 한다.

## 표의 관계를 객체 관계로 옮긴다

장표의 주문 표와 주문 항목 표를 보고 다음에 답한다. 한 주문이 여러 항목과 연결된 상황이다.

| 질문 | 내 설명 |
|---|---|
| PK는 한 표에서 무엇을 구분하는가? | |
| 항목의 FK는 어느 주문을 가리키는가? | |

FK로 연결된 여러 행을 Java에서는 객체 참조·컬렉션으로 표현할 수 있다. 그림의 화살표를 실제 요청이 오가는 네트워크 선과 혼동하지 않는다.

## 더 궁금할 때 보는 보충 질문

기본 흐름을 먼저 설명할 수 있을 때 뒤 장표와 연결한다. 모두 암기해야 개인 과제를 시작할 수 있는 것은 아니다.

- 같은 객체의 자기 호출이 왜 안쪽 메서드의 새 트랜잭션 설정을 적용하지 못하는가? 이미 시작된 바깥 트랜잭션도 사라지는가?
- 기본 REQUIRED로 바깥 트랜잭션에 참여했다면 최종 commit 경계는 어디인가?
- 예외를 catch했어도 이미 rollback-only라면 최종 commit이 성공하는가?
- clear는 객체 관리를 해제하는데, 왜 DB 삭제나 rollback이 아닌가?
- merge의 반환 객체와 전달한 원본을 왜 구분하는가?
- DB rollback으로 이미 보낸 외부 HTTP 요청이나 이메일까지 자동 취소할 수 있는가?

답변이 어렵다면 새로운 용어를 더 찾기보다 장표의 대상·화살표·시점을 먼저 짚고 질문한다.
