# 트랜잭션과 JPA 코드·그림 읽기

16일 자료의 [28쪽 · 트랜잭션 기본](../2026-11-16/#slide-28)부터 이어간다. 짧은 코드와 장표의 그림을 대응해 어느 줄에서 SQL이 필요한지 예상하고 자기 말로 설명한다. 독립 예제 프로젝트 실행이나 새 테스트 작성은 필수가 아니다. 마지막에는 [본인의 단축 URL 서비스 JPA 전환 과제](SHORT-URL-JPA-ASSIGNMENT.md)에 적용한다.

모르는 DB 용어는 [DB 기초](../shared/db-basics/)에서 확인한다. 설명용 상품은 키보드이고 가격을 30000원에서 25000원으로 변경한다. 설명용 ID를 실제 생성 ID로 가정하지 않는다.

## 부분 성공은 왜 문제일까?

장표에서 상품 가격 변경과 변경 이력 저장이 각각 어디에 있는지 찾는다. 둘은 하나의 기능에서 수행하는 서로 다른 DB 작업이라고 가정한다. 이력 기능은 설명을 위한 것이며 기본 과제로 새로 만들라는 뜻이 아니다.

| 그림에서 읽을 것 | 내 설명 |
|---|---|
| 가격 변경만 저장되고 이력은 실패하면 어떤 상태인가? | |
| 둘이 함께 성공하거나 함께 취소되어야 한다면 어디를 묶어야 하는가? | |
| 이 묶음의 변경 확정과 변경 취소를 각각 무엇이라고 하는가? | |

트랜잭션은 DB 작업의 성공·실패 단위를 정하는 데 사용한다. 모든 외부 행동까지 자동으로 되돌리는 기능은 아니다.

## Service와 프록시는 어디에 있을까?

그림의 호출 순서를 따라가며 세 대상을 찾는다.

- Service: 하나의 업무를 진행하는 애플리케이션 객체.
- Spring 빈: Spring이 만들고 연결해 관리하는 객체.
- 프록시: 실제 Service 호출 앞뒤에 트랜잭션 처리를 적용하는 대리 객체.

| 질문 | 그림의 위치·내 설명 |
|---|---|
| 호출이 실제 Service에 들어가기 전에 무엇을 거치는가? | |
| 정상 실행 뒤 변경을 확정하는 처리는 누가 앞뒤에서 적용하는가? | |
| 왜 Controller 요청 형식보다 Service의 업무 범위에 트랜잭션을 두는가? | |

기본 그림은 다른 객체에서 Spring 빈의 public Service 메서드를 프록시를 통해 호출하는 상황이다. 프록시는 별도 웹 서버가 아니다.

## 객체의 가격과 DB의 가격을 나눈다

상품 객체와 DB 행은 서로 다른 곳에 있다. 왼쪽 객체와 오른쪽 DB 중 지금 값이 바뀐 쪽을 장표에서 가리킨다.

| 시점 | Java 객체 | DB 상태 |
|---|---|---|
| 상품 조회 | 30000 | 30000 |
| 관리 객체의 가격 변경 | 25000 | SQL 반영 전이라면 30000 |
| flush | 25000 | 현재 트랜잭션에서는 25000, 아직 미확정 |
| commit을 선택 | 25000 | 25000으로 확정 |
| commit 대신 rollback을 선택 | 25000이 자동 복원되지 않음 | 기존 30000으로 변경 취소 |

마지막 두 행은 **서로 다른 두 갈래**다. commit한 다음 rollback으로 같은 변경을 되돌리는 순서가 아니다. 다른 트랜잭션에서 보이는 값은 격리 수준 등에 영향을 받는다.

- 내가 설명하는 commit: `________________________________`

## 왜 별도 save 없이 수정될 수 있을까?

장표의 관리 Entity, 조회 당시 값, 현재 값을 각각 찾는다. 일반 쓰기 트랜잭션 안에서 조회한 관리 Entity라는 조건을 붙여 설명한다.

| 그림에서 확인할 것 | 내 설명 |
|---|---|
| 조회 당시 가격과 현재 가격은 무엇이 다른가? | |
| 이 차이는 어떤 과정에서 DB 수정으로 이어지는가? | |
| new로 만들기만 한 객체에도 똑같이 적용되는가? | |
| 같은 컨텍스트에서 같은 ID를 다시 find하면 어떤 객체를 재사용할 수 있는가? | |

객체 필드가 바뀐 순간과 UPDATE 실행, 최종 commit은 구분한다. IDENTITY 전략에서는 ID를 얻기 위해 INSERT가 일찍 실행될 수 있지만 그 자체가 commit이라는 뜻은 아니다.

## 읽기와 쓰기를 구분한다

| 기능 | DB를 읽기만 하는가, 바꾸기도 하는가? | 내가 정할 범위와 이유 |
|---|---|---|
| 단축 코드로 원본 URL만 조회 | | |
| 새 단축 URL 저장 | | |
| 원본 URL 조회와 클릭 수 증가를 함께 수행 | | |

readOnly는 읽기 의도를 전달하는 힌트다. 쓰기를 확실히 차단하는 장치로 생각하지 않는다.

기본 rollback 규칙에서 RuntimeException·Error와 checked exception은 같지 않다. 장표에서 기본 규칙과 별도 설정이 필요한 경우를 구분한다. 예외가 발생했다는 사실뿐 아니라 어떤 예외가 트랜잭션 경계 밖으로 전파되었는지 확인해야 한다.

## 표의 관계를 객체 관계로 옮긴다

장표의 주문 표와 주문 항목 표를 보고 다음에 답한다. 한 주문이 여러 항목과 연결된 상황이다.

| 질문 | 내 설명 |
|---|---|
| PK는 한 표에서 무엇을 구분하는가? | |
| 항목의 FK는 어느 주문을 가리키는가? | |
| 주문 하나에 항목 두 개를 연결하는 선은 어떻게 그리는가? | |
| Java 객체의 items는 표의 단순한 한 열과 같은가? | |

FK로 연결된 여러 행을 Java에서는 객체 참조·컬렉션으로 표현할 수 있다. 그림의 화살표를 실제 요청이 오가는 네트워크 선과 혼동하지 않는다.

## LAZY 코드의 어느 줄에서 조회할까?

다음은 주문 Entity의 관계 필드 발췌다. import·나머지 필드·메서드는 생략했다. OrderItem의 여러 행은 order_id로 주문과 연결된다.

```java
@OneToMany(fetch = FetchType.LAZY)
@JoinColumn(name = "order_id")
private List<OrderItem> items = new ArrayList<>();
```

LAZY는 관계 데이터를 실제로 필요로 할 때 조회할 수 있도록 미루는 방식이다. 다음은 저장소가 주입된 상황의 읽기 코드 발췌이며, 미초기화 관계를 가진 세 주문을 같은 관리 범위에서 다룬다고 가정한다.

```java
List<PurchaseOrder> orders = repository.findAllByOrderByIdAsc();
String label = orders.get(0).getLabel();
int count = orders.get(0).getItems().size();
```

| 코드의 행동 | 그림의 대상·화살표 | 추가 조회가 필요한지·이유 |
|---|---|---|
| 주문 목록을 처음 조회 | | |
| 이미 읽어 온 주문 이름 사용 | | |
| 아직 읽지 않은 items의 크기 확인 | | |
| 이미 읽은 같은 items 재사용 | | |

size를 읽는 지점에서 어떤 데이터가 필요해졌는지 말한다. 단순히 getItems라는 이름이 있다는 사실만으로 모든 실행에서 SELECT가 나간다고 외우지 않는다. 이미 읽었는지, 조회 계획과 캐시 조건이 무엇인지 구분한다.

## 관리 범위가 끝난 뒤 읽으면?

OSIV가 꺼져 있고, 주문 Entity와 연결된 영속성 컨텍스트가 닫혔다고 가정한다. items는 아직 읽지 않은 상태다. 그 뒤 Controller나 JSON 변환 과정에서 items를 읽으면 LazyInitializationException이 발생할 수 있다.

| 질문 | 내 설명 |
|---|---|
| 추가 SELECT에 필요한 관리 범위가 아직 열려 있는가? | |
| 이미 items를 초기화한 경우도 똑같은가? | |
| Entity를 그대로 응답하면 JSON 변환 중 어떤 접근이 생길 수 있는가? | |
| Service의 트랜잭션 안에서 필요한 값을 읽고 DTO로 옮기면 무엇이 달라지는가? | |

DTO에는 응답에 필요한 값을 담고, 미초기화 Entity 참조를 이름만 바꿔 담는 방식과 구분한다. 다만 DTO는 응답 형태다. DTO를 만드는 과정에서 각 주문의 items를 따로 읽는다면 N+1은 여전히 생길 수 있다. 조회 계획까지 함께 정해야 한다.

## N+1의 코드와 왕복을 연결한다

주문 3개를 조회한 뒤 각각의 항목 이름을 읽는 발췌다. 관계를 미리 읽지 않았고 배치·캐시 등의 추가 최적화가 없는 설명 조건이다.

```java
List<PurchaseOrder> orders = repository.findAllByOrderByIdAsc();
for (PurchaseOrder order : orders) {
    for (OrderItem item : order.getItems()) {
        System.out.println(item.getName());
    }
}
```

| 데이터가 필요한 순서 | 장표의 SELECT 왕복 수 | 코드의 어느 부분인가? |
|---|---|---|
| 주문 목록 | | |
| 첫 주문의 항목 | | |
| 둘째 주문의 항목 | | |
| 셋째 주문의 항목 | | |
| 합계 | | |

아래 SQL은 실제 실행 로그가 아니라 필요한 조회의 모양을 보여주는 예시다.

```sql
SELECT id, label FROM purchase_orders ORDER BY id;
SELECT id, name, order_id FROM order_items WHERE order_id = ?;
```

두 번째 조회가 각 주문의 ID에 대해 반복될 수 있다. N은 여기서 항목 행의 수가 아니라 추가 조회가 필요한 주문 수와 연결된다. 이 조건에서는 목록 1회와 주문별 3회로 총 4회다. LAZY라는 표시만으로 모든 경우에 N+1이라고 단정하지 않는다.

## fetch join은 무엇을 바꿀까?

다음 JPQL은 DB 테이블 이름이 아니라 Entity와 필드 이름으로 작성한 조회 발췌다.

```sql
select distinct o
from PurchaseOrder o
left join fetch o.items
order by o.id
```

| 비교할 것 | 기본 조회 후 관계 접근 | fetch join 후 같은 접근 |
|---|---|---|
| 세 주문과 항목을 읽는 왕복 | | |
| 주문 수와 주문명 | | |
| 항목 수와 항목명 | | |
| Service에서 DTO로 바꾸며 관계에 접근할 때 | | |

fetch join은 필요한 관계를 함께 읽도록 ORM에 요청한다. 이 조건에서는 4회가 1회로 줄 수 있지만, **주문·항목의 수와 내용도 같은지** 확인해야 한다. SQL JOIN으로 행을 결합하는 것과 연관 객체 초기화까지 요청하는 JPQL fetch join을 구분한다.

## 시간이 남으면 보는 JPA 이슈

아래는 추가 개발·제출 요구가 아니라 보충 장표를 이해하기 위한 질문이다. 본인의 개인 전환을 시작하기 전에 모두 해결할 필요는 없다.

### 컬렉션 fetch join과 페이지 조회

한 주문에 항목이 여러 개면 SQL JOIN 결과는 주문 하나가 여러 행으로 늘어날 수 있다. 여기에 행 개수 제한을 바로 적용하면 주문 단위 페이지 요구와 충돌할 수 있다. Hibernate가 메모리에서 페이징하며 경고하거나, 설정에 따라 예외로 중단할 수 있다.

- SQL의 행 제한과 응답의 주문 수 제한은 왜 같은 것이 아닌가?
- 주문 ID를 먼저 페이지 조회하고, 그 ID의 관계를 fetch하는 그림은 무엇을 나누는가?
- IN 조건으로 얻은 결과를 왜 원래 ID 페이지 순서로 복원해야 하는가?
- 전체 건수가 필요한 Page라면 count 쿼리가 추가될 수 있는데, 왜 무조건 두 쿼리라고 외우면 안 되는가?

### 벌크 UPDATE와 오래된 객체 값

JPQL 벌크 UPDATE는 관리 객체를 하나씩 변경 감지하는 경로를 거치지 않고 DB를 직접 갱신한다. 이미 읽어 온 객체의 값은 그대로 남을 수 있다.

- DB 값이 바뀌어도 같은 관리 객체를 읽으면 이전 값이 보일 수 있는 이유는?
- 필요한 변경 flush → 벌크 처리 → clear → 재조회는 각각 무엇을 하는가?
- clear를 DB 삭제라고 생각하거나 미반영 변경을 가진 채 바로 clear하면 무엇을 놓치는가?

### 동시에 증가한 클릭 수가 사라지는 경우

클릭 수 10을 요청 A와 B가 각각 읽고 둘 다 11을 저장하는 그림을 본다. 두 요청이 성공했다는 사실만으로 최종 값 12를 보장할 수 없다.

- @Transactional만으로 이런 갱신 손실이 모두 방지되는가?
- @Version이 있는 낙관적 잠금은 어떤 충돌을 감지하는가? 감지만 하면 자동으로 재시도까지 끝나는가?
- 충돌이 flush 또는 commit에서 드러나면 재시도 경계는 어디에 정해야 하는가?
- DB에서 값을 직접 1 증가시키는 원자적 UPDATE와 객체를 읽어 1을 더해 저장하는 것은 무엇이 다른가?

코드와 그림은 원리 설명용이다. 특정 프로젝트에서 실행하거나 성능 개선을 측정한 결과로 제출하라는 뜻은 아니다.

## 더 궁금할 때 보는 보충 질문

기본 흐름을 먼저 설명할 수 있을 때 뒤 장표와 연결한다. 모두 암기해야 개인 과제를 시작할 수 있는 것은 아니다.

- 같은 객체의 자기 호출이 왜 안쪽 메서드의 새 트랜잭션 설정을 적용하지 못하는가? 이미 시작된 바깥 트랜잭션도 사라지는가?
- 기본 REQUIRED로 바깥 트랜잭션에 참여했다면 최종 commit 경계는 어디인가?
- 예외를 catch했어도 이미 rollback-only라면 최종 commit이 성공하는가?
- clear는 객체 관리를 해제하는데, 왜 DB 삭제나 rollback이 아닌가?
- merge의 반환 객체와 전달한 원본을 왜 구분하는가?
- DB rollback으로 이미 보낸 외부 HTTP 요청이나 이메일까지 자동 취소할 수 있는가?

답변이 어렵다면 새로운 용어를 더 찾기보다 장표의 대상·화살표·시점을 먼저 짚고 질문한다.
