# 11월 23일 · 트랜잭션과 단축 URL JPA 전환

## 출발과 진행

16일 자료의 [28쪽 · 왜 Service에 @Transactional을 붙일까?](../2026-11-16/#slide-28)부터 이어간다. 19일 과제를 모두 완료했다고 가정하지 않는다. 독립 예제 프로젝트의 실행·테스트·완성 코드 읽기를 수업의 출발 조건으로 두지 않는다. 짧은 Java·SQL 발췌는 그림의 어느 지점에서 조회가 발생하고 어떻게 바뀌는지 읽는 데 사용한다. 강사 코딩 시연도 필수가 아니다.

상품 가격이 30000원에서 25000원으로 바뀌는 하나의 그림을 따라간다. 먼저 부분 성공이 왜 문제인지 확인하고 트랜잭션·Service·프록시를 소개한다. 관리 Entity와 변경 감지, flush 뒤 commit 또는 rollback으로 갈리는 흐름을 이해한 다음 readOnly와 기본 예외 규칙으로 확장한다. 이후 관계의 PK·FK와 Java 참조, LAZY와 DTO, N+1 왕복과 fetch join을 연결한다. 보충 자료와 공식 문서 뒤, 맨 마지막 장표에서 본인의 단축 URL 서비스 JPA 전환 과제를 안내한다.

본문에서는 기본 조건과 정상 흐름을 먼저 설명한다. 자기 호출·REQUIRED 참여·clear·persist/merge·세부 튜닝은 뒤 보충으로 남기고, 용어가 나오기 전에 어떤 문제를 다루는지 먼저 짚는다. 예외를 한꺼번에 나열하지 않는다. 교재 CH 11의 JDBC 접근과 수업의 JPA 설명을 구분하고, 교재에 없는 JPA 장·쪽수를 지정하지 않는다.

4시간 중 개인 전환 착수와 질문에 85분 안팎을 확보한다. 나머지 시간은 트랜잭션과 영속성 약 75분, 관계와 조회 약 50분, 중간 휴식과 정리 약 30분을 기준으로 유연하게 조절한다. 고정 시간표나 교육생에게 요구하는 제한 시간이 아니다. 이해가 더 필요하면 고급 보충을 생략하고 기본 흐름과 개인 적용에 집중한다.

## 코드와 그림을 읽는 순서

1. 상품 객체와 DB 행이 서로 다른 곳에 있음을 확인한다. 왼쪽·오른쪽 중 지금 바뀐 값이 무엇인지 묻는다.
2. Service의 업무 범위와 Spring 빈을 설명한 뒤 프록시가 호출 앞뒤에서 트랜잭션을 처리하는 그림을 읽는다. 프록시를 별도 서버로 설명하지 않는다.
3. 일반 쓰기 트랜잭션에서 조회한 관리 Entity의 현재 값과 조회 당시 값을 비교한다. 새로 만들기만 한 객체나 분리 객체에 변경 감지를 일반화하지 않는다.
4. 객체 변경 → flush → commit 또는 rollback의 두 갈래를 따라간다. commit 후 rollback으로 같은 변경을 취소하는 순서로 읽지 않는다.
5. SQL 실행과 확정은 다르며 rollback은 Java 필드를 자동 복원하지 않는다고 확인한다. 최종 commit 자체도 제약조건 등으로 실패할 수 있다.
6. 주문 행과 항목 행의 PK·FK 연결을 Java 객체 관계로 옮긴다. 장표와 작업지는 같은 단방향 OneToMany LAZY·JoinColumn(order_id) 읽기 매핑을 사용한다. 저장 전파 설정은 이번 관계 조회 설명에 추가하지 않는다. 관계 필드는 원본 표의 새 열과 같다는 뜻이 아니다.
7. 목록 조회와 getItems() 접근을 구분해 짧은 코드의 어느 줄에서 SELECT가 필요한지 예상한다. 관계에 접근하기 전과 후의 왕복 화살표를 읽는다. 관리 컨텍스트 종료 뒤 미초기화 관계의 LazyInitializationException을 설명하고, 필요한 데이터를 Service 범위 안에서 읽어 DTO로 구성하는 흐름으로 연결한다.
8. 세 주문을 반복하면서 항목을 읽는 코드와 JPQL fetch join을 비교한다. 같은 결과를 여러 왕복과 한 왕복으로 가져오는 그림을 읽고 SQL 수 감소뿐 아니라 주문·항목 내용도 같은지 묻는다. DTO는 응답 형태이고 fetch join 등은 조회 계획이라는 차이도 짚는다.

[이해 확인 작업지](BEGINNER-WORKSHEET.md)는 짧은 코드의 줄과 그림의 화살표를 대응하고 자기 말로 설명하는 질문으로 사용한다. 코드를 모두 작성하거나 ZIP을 실행할 필요는 없다. 기존 주문 랩 자료는 보관하지만 이번 본문에서 다운로드·실행·별도 제출을 요구하지 않는다.

## 본문에서 지킬 정확성

- 기본 예시는 Spring이 관리하는 빈의 public Service 메서드를 다른 객체에서 프록시를 통해 호출한 일반 쓰기 트랜잭션이다.
- flush는 DB와 SQL을 동기화하는 동작이고 commit은 트랜잭션 확정이다. INSERT가 일찍 보일 수 있는 IDENTITY도 commit과 구분한다.
- Spring 기본 rollback은 RuntimeException·Error가 경계 밖으로 전파되는 경우를 중심으로 설명한다. checked exception의 rollback은 별도 정책이 필요하다.
- readOnly는 힌트이며 쓰기 차단 보장이 아니다. 리다이렉트에서 클릭 수를 수정한다면 쓰기 작업이다.
- DB rollback은 Java 메모리나 외부 HTTP·이메일을 자동 취소하지 않는다. 실패 뒤 DB 결과는 새 트랜잭션에서 확인한다.
- LAZY라고 언제나 N+1이 되는 것은 아니고 EAGER로 바꾼다고 자동 해결되지 않는다. 미리 읽었는지, 실제 접근했는지, 조회 방식과 캐시 조건 등을 구분한다.
- OSIV가 꺼져 있고 관리 컨텍스트가 닫힌 뒤 미초기화 관계에 접근하면 LazyInitializationException이 발생할 수 있다. 이미 초기화된 관계와 구분한다. Entity를 JSON으로 변환할 때 관계 접근으로 쿼리나 예외가 발생할 수 있으므로 필요한 값을 Service 안에서 읽고 DTO로 전달한다. DTO로 바꾸는 과정에도 관계별 SELECT가 반복될 수 있어 DTO 자체가 N+1 해결책은 아니다.
- 주문 3개에서 4 SELECT, fetch join에서 1 SELECT는 준비가 끝난 같은 조건의 설명이다. 모든 프로젝트에 같은 숫자가 보장된다고 말하지 않는다.

## JPA 이슈 보충을 사용할 때

자기 호출에서는 안쪽 메서드의 새 트랜잭션 설정이 적용되지 않으며 기존 바깥 트랜잭션이 없어진다는 뜻은 아니다. 기본 REQUIRED로 참여했다면 최종 commit 경계는 바깥에 있다. 예외를 catch하고 정상 반환하면 다른 rollback-only 표시가 없는 한 commit될 수 있고, 이미 rollback-only라면 catch해도 최종 commit이 실패할 수 있다.

clear는 객체 관리를 해제하는 동작이며 DB 삭제·rollback이 아니다. 미반영 변경이 있으면 손실될 수 있다. persist와 merge는 객체 관리 방식이 다르며 merge는 원본을 무조건 관리 상태로 만드는 작업이 아니다. 이런 세부 사항은 정상 흐름이 정리된 뒤 질문이 있을 때 연결한다. 아래 세 이슈는 기본 관계·N+1 흐름을 이해한 뒤 시간에 따라 고른다. 별도 구현·테스트 제출 과제로 추가하지 않는다.

- 컬렉션 fetch join과 Pageable: SQL 행 제한이 주문 단위 페이지와 충돌할 수 있다. Hibernate가 메모리에서 페이징하며 경고하거나 설정에 따라 예외를 낼 수 있다. ID를 먼저 페이지 조회하고 해당 ID의 관계를 fetch한 뒤 원래 ID 순서를 복원하는 과정을 그림으로 읽는다. IN 조건의 결과 순서는 보장되지 않으며 Page 전체 건수 계산에는 count 쿼리가 추가될 수 있다.
- JPQL 벌크 UPDATE: 관리 객체의 변경 감지 경로를 거치지 않고 DB를 직접 갱신하므로 이미 읽은 객체 값이 오래된 상태로 남을 수 있다. 필요한 변경 flush → 벌크 처리 → clear → 재조회 순서를 구분한다. clear 전에 미반영 변경을 버리지 않도록 주의한다.
- 동시 클릭 증가: 두 요청이 10을 읽고 각각 11을 쓰는 그림에서 갱신 손실을 찾는다. @Version 낙관적 잠금은 충돌을 감지하는 방식이며 자동으로 모든 재시도를 해 주지 않는다. 충돌은 flush·commit에 드러날 수 있고 재시도 범위·횟수를 정해야 한다. 원자적 UPDATE 대안과 조회 결과의 컨텍스트 정합성도 구분한다.

EntityGraph·배치 튜닝 등은 필요할 때 참고한다. 자료의 코드·SQL은 동작 원리 설명용 발췌이며, 교육생 프로젝트나 독립 예제를 실제 실행한 결과라고 주장하지 않는다.
