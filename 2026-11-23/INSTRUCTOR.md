# 11월 23일 · 트랜잭션과 단축 URL JPA 전환

## 출발과 진행

16일 자료의 [28쪽 · 왜 Service에 @Transactional을 붙일까?](../2026-11-16/#slide-28)부터 진행하지 못한 내용을 이어간다. 19일 상품 전환을 완료했다고 가정하거나 관계 실습부터 시작하지 않는다. 발표나 이전 과제의 전체 재구현을 추가 출발 조건으로 요구하지 않는다.

오늘 흐름은 트랜잭션 기본과 실제 적용 → 관리 Entity 수정과 SQL·객체·DB 상태 → 관계·지연 로딩·N+1 → 본인의 단축 URL 서비스 JPA 전환이다. 교재 CH 11의 JDBC 접근과 수업의 JPA 구현을 구분한다. 교재에 없는 JPA 장이나 쪽수를 지정하지 않는다.

4시간 안에서 조절할 권장 범위는 트랜잭션 약 70분, 남은 영속성·SQL 확인 약 25분, 관계·지연 로딩·N+1 약 35분, 개인 전환 착수·질문 약 80분, 중간 휴식·마무리 약 30분이다. 고정 시간표가 아니라 이해도에 따른 운영 기준이다. 진도가 밀리면 주문 랩 실행과 고급 보충을 선택으로 돌리고 개인 프로젝트 전환에 착수할 시간을 확보한다. 강사 코딩 시연은 필수가 아니다. 설명 후 교육생이 직접 예상하고 확인하게 한다.

## 트랜잭션 설명에서 확인할 것

- 상품 30000원을 25000원으로 수정하는 예제로 이전 내용과 연결한다. 관리 Entity와 새로 만들기만 한 객체를 구분한다.
- Spring이 관리하는 빈의 public Service 메서드를 다른 객체에서 프록시를 통해 호출하는 기본 상황을 사용한다. 시작·참여 → 메서드 실행 → flush·commit 또는 rollback으로 그림을 읽는다.
- 기본 REQUIRED는 기존 트랜잭션이 있으면 참여한다. 내부 메서드의 정상 반환은 최종 commit이 아니다. 정상 반환 이후 최종 commit에서 제약조건 오류 등이 발생할 수 있다.
- 일반 쓰기 트랜잭션 안에서 조회한 관리 Entity를 바꾸면 별도 save 없이 변경 감지를 적용할 수 있다. 분리 객체와 비영속 객체에 일반화하지 않는다.
- flush는 SQL 동기화, commit은 확정, clear는 관리 해제다. clear는 DB 삭제·rollback이 아니고, 미반영 변경이 있으면 주의한다. IDENTITY는 ID 획득을 위해 INSERT가 일찍 실행될 수 있다.
- 기본 rollback은 RuntimeException·Error가 경계 밖으로 전파되는 경우를 중심으로 설명한다. checked exception은 필요 시 rollbackFor 등의 정책을 정한다.
- 예외를 catch하고 정상 반환하면 다른 rollback-only 표시가 없는 한 commit될 수 있다. 이미 rollback-only라면 예외를 잡았어도 최종 commit이 실패할 수 있다.
- 자기 호출에서는 안쪽 메서드의 새 트랜잭션 설정이 적용되지 않는다. 이미 시작된 바깥 트랜잭션 자체가 없어진다는 뜻은 아니다. 해결 예시는 별도 Service 빈을 외부에서 호출하는 구조로 읽는다.
- readOnly는 힌트이며 강제 쓰기 차단 장치가 아니다. 리다이렉트 시 클릭 수를 수정하면 쓰기 작업이다. 바깥 readOnly 트랜잭션에 참여한 내부 메서드의 애너테이션만으로 쓰기 환경이 새로 생기지는 않는다.
- DB rollback은 이미 바뀐 Java 필드나 외부 HTTP·이메일을 자동으로 되돌리지 않는다. 실패 뒤의 DB 확인은 별도 새 트랜잭션에서 한다.

## 관계와 SQL

주문 3행과 항목 6행의 PK·FK를 먼저 연결한다. 한 주문의 label과 items에 접근할 때 SQL이 어떻게 달라지는지 예상한다. LAZY 표기만으로 N+1을 단정하거나 EAGER로 바꾸면 해결된다고 설명하지 않는다. 필요한 관계를 Service 트랜잭션 안에서 읽고 DTO를 구성하는 방향으로 연결한다. Entity 직렬화나 OSIV를 켜는 방식으로 문제를 우회하도록 요구하지 않는다.

[쉬운 관찰 작업지](BEGINNER-WORKSHEET.md), [DB 기초](../shared/db-basics/), [order-query-lab ZIP](assets/order-query-lab.zip)을 참고할 수 있다. 주문 랩은 선택 관찰 자료이며 별도 주문 API 개발이나 별도 Issue·PR 제출은 필수가 아니다.

기존 ZIP과 `shared/order_sources.py`의 6개 참고 파일은 변경하지 않는다. PurchaseOrder → OrderItem의 단방향 OneToMany LAZY·JoinColumn·Cascade ALL이라는 최소 예제다. 책의 전체 주문 관리 요구를 구현한 코드가 아니다.

관찰할 경우 order-query-lab 폴더에서 제공 테스트를 실행한다.

```sh
./gradlew test --tests '*PersistenceContextTest' --info --rerun-tasks
./gradlew test --tests '*OrderQueryTest' --info --rerun-tasks
./gradlew test
```

Windows는 gradlew.bat를 사용한다. `--rerun-tasks`는 이전 성공 결과로 생략되지 않게 하고 `--info`는 테스트의 SQL 출력을 확인하는 데 쓴다. 콘솔이 길면 build/reports/tests/test/index.html의 Classes에서 해당 클래스의 Standard output을 연다. 디버거의 자동 컬렉션 펼침이 추가 SQL을 만들 수 있으므로 최종 수는 일반 실행으로 다시 확인한다.

측정은 seed flush → EntityManager.clear → Hibernate statistics.clear 뒤 시작한다. flush는 준비 SQL 동기화, EntityManager.clear는 준비 객체 분리, statistics.clear는 숫자 초기화다. 같은 동작이 아니다. 준비 SQL을 제외하고 주문 목록과 각 items만 읽는 통제된 조건에서 기본 4 SELECT와 fetch join 1 SELECT를 비교한다. 주문 3개·항목 6개의 개수와 이름도 같아야 한다.

prepareStatementCount는 원래 모든 prepared statement 수다. 이 실험의 측정 구간이 SELECT뿐이므로 SELECT 수로 비교할 수 있다. 캐시·배치 페치·이미 초기화된 관계에 따라 숫자는 달라질 수 있다. 일반 SQL JOIN과 연관 객체 초기화를 요청하는 JPQL fetch join도 구분한다. EntityGraph·배치 튜닝·컬렉션 fetch join의 페이지네이션은 보충으로 남긴다.

## 본인 단축 URL 서비스 전환

필수 과제는 [나만의 단축 URL 서비스 JPA 전환](SHORT-URL-JPA-ASSIGNMENT.md)이다. 핵심 요구는 장표 안에서도 읽을 수 있게 안내한다. 기존 생성·리다이렉트·입력 검증·없는 코드 처리와 이미 구현한 부가 기능·프론트 계약을 유지하며 저장소를 교체한다. 새 통계·어드민·수정·삭제 기능 전체를 기본 요구로 추가하지 않는다.

Entity와 DTO, 코드 고유 제약조건, Repository 연결, Service 쓰기 트랜잭션, 파일·서버 DB 재시작 보존을 확인한다. 기존 도메인 Repository가 있다면 어댑터로 교체할 수 있다. 기존 데이터가 있으면 백업·스키마 변경·이관 필요성을 검토한다. 메모리 DB나 create/create-drop으로 재시작 보존을 확인했다고 하지 않는다.

QA 항목은 교육생이 본인 기능에 맞춰 작성한다. 기존 동작 유지와 정상 commit·실패 rollback은 반드시 근거를 남긴다. 수동 확인도 가능하며 새 테스트 작성이 필수는 아니다. 로컬 임시 강제 예외 실험 뒤에는 실패 요청이 끝난 다음 새 트랜잭션으로 조회한다. 동일 객체 값이나 SQL 로그만으로 commit을 증명하지 않는다. 실패 실험용 엔드포인트와 강제 예외는 제출 전에 제거한다.

추가 과제는 검색·정렬·페이지 조회 → 수정과 이력의 원자성 → 고유 코드 충돌과 동시성 순으로 선택한다. 기본 전환이 끝난 뒤 진행하며 완료하지 못한 심화를 필수 미완료로 처리하지 않는다.

백엔드는 AI 도움을 받아도 동작과 트랜잭션 경계를 본인이 설명한다. 프론트는 기존 화면을 유지하거나 AI로 보완하되 순수 HTML·CSS·JavaScript만 사용하고 외부 라이브러리 CDN은 사용하지 않는다. 프롬프트는 자율이다.

### 29. 필요한 항목을 fetch join으로 함께 읽기

JPQL은 테이블명이 아닌 Entity와 속성명을 사용합니다. 일반 join만으로 연관관계 초기화가 보장되는 것은 아닙니다. 참고 구현과 동일 쿼리입니다.

### 30. SQL을 줄여도 결과 값은 같아야 함

준비 SQL과 측정 SQL을 섞지 않습니다. prepareStatementCount는 모든 준비된 SQL문 수지만 이 측정 구간에는 SELECT만 있습니다. EAGER로 바꾸는 것만으로 N+1 해결이 보장되지 않습니다.
