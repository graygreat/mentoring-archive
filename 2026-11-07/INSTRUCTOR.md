## 실습 진행 기준

개념 구간에서는 코드와 요청 흐름을 읽고 설명합니다. 프로젝트 생성, 설정 변경, Java 파일 작성과 실행은 모두 실습 A 이후에 진행합니다. 슬라이드 순서와 시간표 모두 이 기준을 따릅니다.

### 실습 A

같은 패키지에 상품 객체, 저장소 인터페이스와 메모리 구현체, 없는 상품 예외, Service를 만듭니다. `ProductServiceTest`는 서버 없이 실행하는 테스트입니다. `@SpringBootTest`나 DB 연결은 사용하지 않습니다.

- 생성 성공, 잘못된 가격, 없는 id 테스트 통과를 확인합니다.
- 인터페이스를 주입받는 생성자를 찾고, 실제 연결되는 구현체를 설명하게 합니다.
- 아직 Controller가 없으므로 `/products`의 404를 실습 실패로 판단하지 않습니다.

### 포트 설정·AOP

실습 A의 실행 확인 뒤 `server.port=8081`로 변경·재시작해 보고, 뒤의 API 요청을 위해 8080으로 되돌립니다. Boot 4.x에서는 `spring-boot-starter-aspectj`를 추가합니다. `TimingAspect`를 작성하되 `proceed()`와 `finally`의 의미를 먼저 읽습니다. HTTP를 통한 Service 호출 뒤 콘솔 로그를 확인합니다. 순수 Java 테스트의 `new ProductService(...)`에는 프록시가 없다는 점을 비교합니다.

### 실습 B·C

Request DTO·Response DTO·Controller·전역 예외 핸들러를 같은 프로젝트에 추가합니다. 검증 어노테이션을 포함한 최종 코드가 제공되므로, API의 정상 요청부터 확인하고 검증·예외 처리 단계에서 앞서 배운 규칙과 실제 응답을 연결합니다. 모든 파일이 완성되기 전에는 중간 단계 오류가 있을 수 있습니다.

- `POST /products`: 201, Location, 생성 응답의 id 확인
- `GET /products`: 200과 배열, 비어 있으면 `[]`
- `GET /products/{id}`: 생성 응답의 실제 id로 조회
- 공백 이름·음수 가격·빠진 가격·문자열 가격: 각각 400, 목록 수 불변
- 존재하지 않는 id: 404와 오류 JSON
- 앞뒤 공백이 있는 정상 이름: 201, 공백이 제거된 이름
- 서버를 다시 시작하면 메모리 저장 상품과 번호가 초기화됨

브라우저 주소창은 GET 확인에 사용합니다. POST는 사용 가능한 API 도구 또는 슬라이드의 JSON 파일 기반 curl 명령을 사용합니다. 프로젝트에 파일을 새로 추가하거나 바꾼 뒤 저장·재시작합니다. 같은 서버를 두 번 실행하지 않습니다.

## 슬라이드별 진행 참고

### 02. 개념 전체 → 실습 → 설명

휴식 포함 8시간, 45분 수업 8회 기준 순수 수업 360분을 가정합니다. 실습 155분과 발표·공유 25분으로 180분을 확보합니다. 점심이 이 8시간에 포함되면 AOP 실습을 관찰로 줄이고 필수 API와 발표를 우선합니다. 학생용 슬라이드에는 분 단위 시간을 넣지 않습니다.

### 03. 오늘 함께 볼 챕터

목차에 기반해 독립적으로 작성한 예제입니다. 본문이나 책 예제를 그대로 재현하지 않습니다. 9장의 List 구현에서 Map 기반 메모리 구현으로 확장하며 이유를 비교합니다. 필수 범위는 생성·목록·단건 조회입니다.

### 04. List로 상품을 관리했다면

List가 틀린 선택이라는 뜻이 아닙니다. 같은 요구를 다른 자료구조로 표현하며 저장 코드를 Repository 뒤에 둡니다. 이번 예제는 DB 없이 재시작 시 초기화됩니다.

### 07. 개념을 먼저 익히고, 실습을 이어갑니다

미리 완성된 프로젝트나 압축 파일을 배포하지 않습니다. 모든 파일은 Initializr로 생성한 본인 프로젝트에서 만듭니다. 코드 전체 버튼은 슬라이드 예제의 참고 보기이며 편집 기능이 아닙니다.

### 09. 직접 만들기와 전달받기

생성자 주입은 일반 Java에서도 가능합니다. Spring은 이를 컨테이너의 빈 생성·연결에 적용합니다.

### 17. @Bean은 메서드의 반환 객체를 등록

이 코드를 추가하려면 MemoryProductRepository의 @Repository를 제거해야 같은 역할을 이중 등록하지 않습니다. Configuration과 Bean의 import는 org.springframework.context.annotation입니다. 이 예시는 필수 프로젝트에 작성하지 않습니다.

### 18. 등록 · 범위 · 타입을 확인합니다

Qualifier나 Primary는 후보를 의도적으로 여러 개 사용할 때 확장합니다. 초반에는 후보를 하나로 유지합니다. 빈 이름 암기보다 오류 메시지의 required type과 후보 수를 읽게 합니다.

### 19. 여러 요청이 Service 하나를 공유합니다

JVM 전체에 모든 클래스 객체가 하나라는 뜻이 아닙니다. 컨테이너가 다르거나 같은 클래스의 빈 정의가 여러 개면 객체도 달라질 수 있습니다. 요청 스코프 등은 이름만 소개하고 구현하지 않습니다.

### 20. 요청별 값은 지역 변수로 다룹니다

Repository의 저장소는 의도적으로 공유하는 상태입니다. 공유 상태와 요청별 임시 값을 구분합니다. 이번 메모리 구현은 ConcurrentHashMap과 AtomicLong을 사용하되 트랜잭션이나 영속성을 제공하지 않습니다.

### 21. IoC와 DI를 자신의 코드로 설명

예시 답변: ProductService가 ProductRepository에 의존하며 Spring이 구현 빈을 전달합니다. 인터페이스를 기준으로 받으므로 Service를 유지하면서 저장 구현이나 테스트용 객체를 바꿀 수 있습니다.

### 23. 함께 사용하는 라이브러리 묶음

스타터는 의존성 묶음입니다. 클래스가 라이브러리에 생긴 것과 컨테이너에 빈이 등록된 것은 구분해야 합니다. 필요한 조건에 따라 자동 설정이 적용됩니다.

### 29. 프록시를 통과하는 호출을 비교

개념 설명 뒤 집중 실습에서 프로젝트와 Aspect를 작성하고, HTTP 요청으로 적용을 확인합니다. 이 표는 Spring의 기본 프록시 기반 AOP에 대한 설명이며 AspectJ weaving까지 일반화하지 않습니다. final/private 제약은 질문이 나오면 설명합니다.

### 30. 자동 설정과 AOP를 설명해 봅시다

답변은 정의 암기보다 오늘의 dependencies·TimingAspect·주입 코드를 근거로 하게 합니다. DI와 AOP는 서로 다른 개념이며 DI 자체가 모든 메서드 호출을 가로채는 것은 아닙니다.

### 32. 화면의 역할과 업무의 역할을 나눕니다

Model을 특정 Entity 클래스 하나나 DB와 동일시하지 않습니다. 서버 템플릿 화면을 반환하는 Controller와 JSON을 반환하는 RestController를 구분하되 웹 MVC 기반을 공유합니다.

### 33. DispatcherServlet이 흐름을 조율합니다

DispatcherServlet은 프런트 컨트롤러입니다. HandlerMapping으로 핸들러와 인터셉터 정보를 찾고 HandlerAdapter에 실행을 위임합니다. Service와 Repository는 Controller가 호출하는 애플리케이션 코드이며 DispatcherServlet이 모두 직접 실행하는 것은 아닙니다.

### 35. @Controller와 @RestController

ResponseEntity 반환처럼 명시적으로 응답을 다루는 경우도 있습니다. 무조건 모든 Controller String이 화면이라는 식으로 일반화하지 않습니다. 현재 예제의 Controller는 RestController입니다.

### 36. 명사로 대상을, 메서드로 동작을

URI 모양만으로 REST의 모든 제약을 충족하는 것은 아닙니다. 오늘은 리소스·메서드·상태 코드·표현의 일관성을 연습합니다.

### 39. JSON 입력과 응답에서 하는 일

JSON 변환 방법이 setter/getter만 있는 것은 아닙니다. record나 생성자 바인딩 등은 이후 확장합니다. 이번 예제는 책의 getter/setter 학습에 맞춰 Java Bean 형태를 사용합니다. 생성자를 선언하지 않은 요청 DTO에는 기본 생성자가 생깁니다.

### 40. 상태 · 헤더 · 본문을 함께 정합니다

이 예시는 읽기 쉽게 단순화한 HTTP 메시지입니다. 실제 헤더 값·순서는 실행 결과를 기준으로 확인합니다. 상품 id는 예시이며 실제 생성 응답의 id를 사용합니다.

### 43. 잘못된 DTO는 Service 호출 전에 멈춥니다

실습과 발표를 합쳐 순수 학습시간 약 180분을 확보합니다. 팀 수에 맞춰 팀별 발표 시간을 조절하고 모든 팀이 최소 하나의 실행 결과와 코드 관계를 설명하게 합니다. 개인정보나 비밀키가 화면에 없도록 일반 학습 자료를 사용합니다.

### 105. 다음에는 저장소를 바꿉니다

DB 전환 시 트랜잭션·식별자 생성·조회 방식 등 구현과 계약 조정이 필요할 수 있습니다. 아무 코드도 바꾸지 않고 DB가 저절로 붙는다고 설명하지 않습니다. 책 13·14장은 종합 과제로 연결합니다.

### 108. 실습 프로젝트에 없는 기능을 직접 구현

기존 8시간 수업의 실습 시간표를 늘리지 않습니다. 실습과 발표·정리를 마친 뒤 별도 수행할 과제입니다. 정답 코드나 구현 시연 없이 요구사항을 안내하고 질문을 받은 뒤 제출 결과를 피드백합니다. 마감은 이 자료에서 정하지 않습니다.

### 109. 이름으로 상품 목록 검색

검색어의 앞뒤 공백을 제거한 뒤 부분 일치 검색을 수행합니다. 영문 대소문자는 구분합니다. 이름 검색과 가격 필터는 같은 GET /products 목록 API에 누적 적용합니다. 상품 데이터는 조회만 하며 기존 목록·단건 조회도 유지합니다.

### 110. 가격 조건과 이름 검색을 함께 적용

기준 상품을 먼저 생성하고 기존 저장 상품에 따라 결과가 달라질 수 있음을 확인합니다. 조회 전후 저장된 상품과 전체 목록 개수가 같아야 합니다. 조건에 맞는 상품이 없으면 200과 빈 배열을 반환합니다. 0원 상품과 상한값과 같은 가격을 경계값으로 테스트합니다. 필터 결과를 저장소에 덮어쓰지 않습니다.

### 111. 상품 이름과 가격을 전체 수정

경로의 {id}에는 생성 응답에서 받은 실제 id를 사용합니다. Product의 필드는 final이므로 기존 id를 유지한 새 Product로 교체하는 방법을 설계할 수 있습니다. 기존 저장 메서드로 새 id를 발급하지 않습니다. 구현 정답은 제공하지 않습니다.

### 112. 수정에 실패하면 기존 값을 보존

성공 요청과 각 오류 조건을 분리해 테스트합니다. 실패 전후 단건과 목록을 비교해 상품을 일부만 변경하거나 삭제하지 않았다는 결과를 제출하게 합니다. 수정·삭제 뒤에도 이름 검색·가격 필터와 기존 API를 유지합니다.

### 113. 상품을 삭제하고 후속 요청 확인

삭제할 상품과 유지할 상품을 먼저 만듭니다. 204 응답에 JSON이나 문자열 본문을 넣지 않습니다. 경로의 {id}에는 생성 응답에서 받은 실제 id를 사용합니다. 다른 실행의 id나 빈 서버 상태를 가정하지 않습니다.

### 114. 코드와 실행 결과로 설명합니다

저장소 링크 또는 코드 파일 등 확인 가능한 형태로 제출합니다. GitHub PR은 필수가 아닙니다. 평가에서는 요구사항 충족, 기존 API 회귀 여부, 성공·실패 테스트와 설명 근거를 확인하고 결과를 피드백합니다. 별도의 마감은 임의로 설정하지 않습니다.
