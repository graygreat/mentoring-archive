## CH 14 · 주문 관리 API

저자 공식 저장소의 14-1 시작 프로젝트를 활용합니다. 14-2 완성 코드를 수업 중 열지 않습니다. POST /orders, PATCH /orders/{orderId}, GET /orders/{orderId}, GET /orders?state={state}, PATCH /orders/{orderId}/cancel을 구현합니다. 상품명과 가격은 주문 시점 값을 보관하고 여러 상품의 가격×수량을 합산합니다. 신규 상태는 CREATED이며 재고를 차감합니다. POST 본문은 id·amount 항목의 배열입니다. 주문 응답은 id·orderedProducts·totalPrice·state이며, orderedProducts의 항목은 id·name·price·amount입니다. 상태 값은 CREATED·SHIPPING·COMPLETED·CANCELED이고 강제 변경 본문은 state입니다.

어느 상품이라도 없거나 재고가 부족하면 주문을 생성하지 않고 모든 상품 재고를 보존합니다. 상품·주문 없음은 404, 재고 부족과 CREATED가 아닌 주문 취소는 책의 계약대로 500입니다. 이 500 계약을 일반적인 REST 설계 원칙으로 가르치지 않습니다. 강제 상태 변경에 임의의 상태 전이 제한을 더하지 않습니다. 취소 후 주문 기록을 조회할 수 있어야 하며 재고 복원은 책의 필수 기능으로 추가하지 않습니다.

## JPA 입문 범위

12일 JDBC의 SQL·결과 변환과 비교해 ORM을 설명합니다. JPA는 표준, Hibernate는 구현체, Spring Data JPA는 Repository 구현을 줄여 주는 기능입니다. SQL과 DB 연결 설정은 계속 필요합니다. Entity와 기본 키·생성자, EntityManager가 관리하는 영속성 컨텍스트, 같은 컨텍스트에서 식별자로 조회한 객체의 1차 캐시, 트랜잭션 안의 관리 Entity 변경 감지, flush와 commit의 차이를 다룹니다.

관계 매핑·지연 로딩·N+1의 상세 구현은 다음 주로 넘깁니다. 16일 Entity·Repository 실행과 SQL 관찰, 19일 저장소 JPA 전환 실습, 23일 관계·지연 로딩·N+1을 이어갑니다. save가 즉시 커밋을 의미하거나 어떤 Java 객체의 변경도 자동 저장된다는 오해를 막습니다.

### 24. 세 가지 이름의 역할

JPA 자체는 특정 DB도 구현체도 아닙니다. Spring Data JPA는 JPA의 대체물이 아니며 Hibernate는 대표 구현체입니다. 이 수업의 일반적인 실행 구성을 기준으로 설명합니다.

### 25. 무엇을 연결할지 정하기

Lombok @NoArgsConstructor가 필수인 것은 아닙니다. 직접 기본 생성자를 작성할 수 있습니다. 수업에서는 기존 Product 도메인과 ProductEntity를 구분합니다. JPA가 검증이나 업무 규칙을 대신하지 않습니다. save는 신규 여부에 따라 persist 또는 merge를 사용하며 호출 즉시 커밋을 보장하지 않습니다.

### 26. 조회한 Entity를 관리하는 작업 공간

영속성 컨텍스트는 DB 자체나 서버 전체의 영구 저장소가 아닙니다. 이 수업은 Service 트랜잭션 안에서 조회·수정하고 종료하는 기본 사용 흐름을 기준으로 설명합니다. 영속성 컨텍스트를 벗어나 분리된 Entity는 변경 감지 대상이 아닙니다.

### 27. 같은 Entity 조회 · 변경 감지

1차 캐시는 같은 영속성 컨텍스트 범위의 식별자 기반 조회에 대한 설명이며 서버 공용 캐시가 아닙니다. JPQL 등 다른 조회는 SQL을 실행할 수 있습니다. 변경 감지와 flush 시점은 실제 SQL 로그로 다음 시간에 확인합니다.

### 28. SQL 실행과 저장 확정은 다릅니다

보통 쓰기 Service 메서드의 @Transactional 경계에서 작업합니다. flush는 커밋 전이나 쿼리 실행 전 등에도 일어날 수 있고 INSERT 실행 시점은 식별자 전략에 따라 달라집니다. 롤백이 Java 객체의 모든 필드까지 자동으로 원상 복구한다는 뜻은 아닙니다. 예외별 롤백 규칙과 프록시는 다음 수업에서 다룹니다.
